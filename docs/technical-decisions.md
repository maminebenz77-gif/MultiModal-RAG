## 1. Overall shape: ports & adapters

Every swappable concern (LLM/embedding/vision/reranker providers, vector store, keyword store) is split into an **abstract interface** (`*/base.py`) and **concrete implementations**, constructed only by a single `factory.py` per module. Calling code depends on the interface, never on a concrete class (`QdrantStore`, `LiteLLMProvider`) directly.

**Why**: the entire premise of the project is that pieces get swapped — chunking strategy, embedding model, vector backend — while iterating. Ports & adapters makes "swap the vector store" a one-file change (the factory), not a grep-and-replace across the codebase. `Retriever` is the one deliberate exception: it's *not* an ABC, because retrieval *method* is chosen per-query by the caller (a UI dropdown), not per-deployment-environment the way providers/stores are — a different axis of variation, so it doesn't fit the same pattern.

**Cost**: an extra layer of indirection for every module, and the discipline of never letting a concrete class leak into calling code (even for something as small as "just check `isinstance(store, QdrantStore)`"). Worth it here because the swapping is real and expected, not hypothetical.

## 2. Environment portability

`RAG_ENV` (an OS environment variable, read *before* pydantic loads anything, since it decides *which* file to load) selects `.env.local` or `.env.server`. Both files populate the same `Settings` model (`pydantic-settings`), so the rest of the app never branches on environment — it just reads `Settings` fields that happen to differ.

**The privacy guard**: on the server profile (`ALLOW_EXTERNAL=false`), `enforce_privacy_guard()` checks every provider's `base_url` against loopback/private IP ranges before construction — an external URL raises immediately, not "might silently phone home." Also forces `HF_HUB_OFFLINE=1`/`TRANSFORMERS_OFFLINE=1` so the moment a `sentence-transformers` model isn't already cached, it fails loudly instead of hanging on a DNS lookup that never resolves on an air-gapped box.

**Trade-off**: this is a *structural* guarantee, not a network-level one — it stops the *application* from calling out, not a compromised dependency from doing so. A real air-gapped deployment still wants network-level isolation (firewall rules) as the actual boundary; the privacy guard is defense sitting inside that boundary, not a replacement for it.

## 3. Providers layer

`LiteLLM` is the mechanism that makes "same code, different backend" possible for LLM/embedding/vision calls — any OpenAI-compatible endpoint (real OpenAI, an internal company gateway, a local vLLM server) is reachable through the same `litellm.completion()`/`litellm.embedding()` call, differing only by `model`/`base_url`/`api_key`. LangChain's own model-wrapper classes were deliberately *not* used for this, even where LangChain is used elsewhere (the generation chain) — those wrappers would reintroduce vendor coupling at exactly the point the whole providers layer exists to avoid.

**Local embeddings** (`SentenceTransformerEmbeddingProvider`) run entirely offline once the model is cached — no network call at all, which is what makes them safe on the air-gapped profile. **Hosted embeddings** (`LiteLLMEmbeddingProvider`) manually batch input (LiteLLM doesn't batch for you, and real APIs cap request size) and retry each batch with exponential backoff; a persistently-failing batch doesn't abort the whole call — already-embedded batches are kept and returned alongside which texts failed, so a caller can decide to use the partial result or retry just the gap. Constructing the underlying `openai.OpenAI` client explicitly (rather than letting LiteLLM build its own internally) turned out to matter for one specific reason: on a corporate network requiring `truststore`'s SSL patch (see below), LiteLLM's own internally-constructed client didn't reliably pick that patch up.

**Corporate proxy support** (`TRUST_SYSTEM_CERTS`): a TLS-inspecting corporate proxy presents certificates signed by an internal CA that the OS trusts but Python's bundled `certifi` CA list doesn't. `truststore.inject_into_ssl()` patches the `ssl` module to defer to the OS trust store instead. Gated behind a settings flag, default off — inert everywhere the flag isn't set, so it never changes behavior on Linux, CI, or a Mac.

**Tool-calling as an optional capability**: `generate_with_tools()` was added to `LLMProvider` for the agent loop (§11) to get structured tool calls back, not just text — as a *concrete* method with a `NotImplementedError` body, not `@abstractmethod`. Making it abstract would have broken every existing subclass (`InternalServerLLM`, every test's `FakeLLM`) that only ever implemented plain `generate()`; an optional capability layered onto a required interface shouldn't force every existing implementer to react the moment the capability is added. `LiteLLMProvider` implements it via `litellm.completion(..., tools=...)`; `InternalServerLLM` inherits the same not-implemented stub its plain `generate()` already has.

## 4. Ingestion

File type is detected from actual file **content** via `libmagic`, not the extension — a renamed or extensionless PDF still routes to the PDF parser. Markdown is the main exception (CSV too, on `libmagic` builds that don't report `text/csv` distinctly): plain text has no distinguishing magic bytes, so `libmagic` can only report `text/plain`, and the dispatcher falls back to the file extension for those cases.

PDF parsing uses `unstructured[pdf]` (poppler + tesseract) rather than `PyMuPDF` — a deliberate choice after flagging that PyMuPDF is AGPL-licensed, which isn't a "we'll deal with it later" concern for anything meant to leave a personal sandbox. DOCX/PPTX/Markdown/CSV/Excel keep their native-library parsers (`python-docx`, `python-pptx`, `markdown-it-py`, stdlib `csv`, `openpyxl`) rather than being funneled through `unstructured` too — `unstructured` earns its dependency weight specifically for PDF's harder extraction problem (layout analysis, OCR fallback), not for formats with a straightforward native parser already available.

Every format-specific parser converges on one common `Element` schema (type, text, metadata: source file, position, page/slide number) — everything downstream (chunking, citations) works against that one shape, never against a format-specific structure.

### How a file becomes Elements, by type

The dispatcher (`ingestion/__init__.py`, `parse_document()`) picks a parser in three steps and stops at the first that answers: (1) the `libmagic` MIME type against a fixed table (PDF, DOCX, PPTX, XLSX, `text/csv`); (2) if the MIME type is one of the ambiguous ones (`text/plain`, `application/octet-stream`, `application/zip`), the file extension (`.pdf .docx .pptx .xlsx .csv .md .markdown`); (3) failing that, a content sniff — the `%PDF` magic bytes, or the internal paths of a ZIP container (`word/document.xml`, `ppt/presentation.xml`, `xl/workbook.xml`). Anything else raises `ValueError`, which `POST /ingest` turns into a 422. Legacy `.doc`, `.ppt` and `.xls` are not supported. The whole parse runs inside one Langfuse `ingest` span, so every LLM call it triggers nests under it (§17).

Every parser returns a flat, ordered list of `Element`s of five types — `TITLE`, `PARAGRAPH`, `TABLE`, `IMAGE`, `CHART` — carrying `source_file`, `position`, and whichever of `page` / `slide` / `sheet` the format has. A table's `text` is markdown; an image's or chart's `description` is text (a vision-model caption for a picture, generated text for a chart), and that description is what later gets embedded.

| Format | Parser | Titles | Tables | Pictures | Charts | Location |
|---|---|---|---|---|---|---|
| PDF | `unstructured` (`hi_res`: poppler + layout model + tesseract) | layout model's "Title" | layout model's "Table", to markdown | vision caption | not detected — just a picture | page |
| DOCX | `python-docx` | styles Title, Heading 1–6 | cell text, to markdown | vision caption | not detected | none |
| PPTX | `python-pptx` | title / centre-title placeholders | cell text, to markdown | vision caption | native chart, read from its own data (no LLM) | slide |
| Markdown | `markdown-it-py` | `#` headings | GFM tables, to markdown | vision caption of a `![](file)` paragraph | none | none |
| CSV | stdlib `csv` | none | 30-row batches, header repeated | none | none | none |
| Excel (`.xlsx`) | `openpyxl` | none | per sheet, 30-row batches, header repeated | vision caption (floating pictures) | native chart, described by an LLM from its XML | sheet |

**PDF.** A PDF carries no structure — just positioned glyphs — so this is the one parser that *infers* it. `hi_res` renders each page, a layout model classifies regions, and tesseract OCRs image regions: `Title` becomes TITLE; `NarrativeText`, `UncategorizedText` and `ListItem` become PARAGRAPH; `Table` becomes TABLE (built from the model's HTML rows, or flattened text if none came back); `Image` becomes IMAGE, bytes kept and captioned by the vision model. If `hi_res` fails for any reason (no local layout model, tesseract/poppler missing, restricted network) it falls back to `fast` — text only, no table structure, no image extraction — and a `RuntimeWarning` surfaces in the ingest response's `ingest_warnings`. Expect the roughest edges here (misread header rows, OCR errors).

**DOCX.** Walks the body in document order, so tables and pictures stay where they were. Known quirk (verified): a paragraph containing an inline picture yields *only* the picture — any text in that same paragraph is dropped. Native Word charts aren't detected; a pasted picture of a chart is an ordinary image.

**PPTX.** Per slide, per shape, in order, first match wins: chart, table, picture, text frame; other shapes are dropped. A native chart's description is built straight from its data model (type, categories, series values) with no vision or LLM call, since the chart's own numbers are strictly more accurate than any caption of it.

**Markdown.** Headings, paragraphs, GFM tables, and paragraphs consisting solely of an image (resolved relative to the `.md` file's folder; a missing file gets a placeholder description). Verified: list items and blockquotes come through as plain paragraphs, so list structure is lost, and fenced code blocks are dropped entirely.

**CSV and Excel.** A spreadsheet can run to thousands of rows, so the one-Element-per-table model above doesn't fit; `ingestion/tabular.py` instead batches rows into `TABLE` Elements of `ROWS_PER_ELEMENT` (30) rows, each rendered as markdown with the header row repeated at its top.

- The first non-blank row is *always* the header. There is no attempt to detect title or note rows above a real header (§19).
- **CSV** is one implicit sheet, read as UTF-8 (a BOM is tolerated).
- **Excel** is processed one worksheet at a time. Values are read with `data_only=True` (a formula cell contributes its last cached result, not the formula); empty cells become empty strings; fully blank rows are dropped. Then the sheet's floating pictures are extracted (via openpyxl's private `_images`; pictures embedded *in* a cell are not) and captioned like any other image. Then its native charts: charts aren't stored per sheet, so each is attributed to its sheet by following the OOXML relationships worksheet → drawing → chart; the chart's own `xl/charts/chartN.xml` is parsed for type, title and series, the series' cell ranges are resolved against the sheet's values, and an LLM writes a short description of what it shows (bar, column, line, area, pie, doughnut and radar families; scatter, bubble, stock and surface charts get a minimal type-and-title description). If no description can be produced, no element is emitted for that chart.
- Not handled: merged cells (only the top-left cell holds a value), several tables on one sheet, a chart that references another sheet, and `.xls`.
- `Element.metadata.sheet` records the sheet but is not yet carried through to chunks, stores or citations.

### What happens to Elements after parsing (every format)

1. **Sections.** `StructureAwareChunker` starts a new section at every `TITLE` element. A section's embeddable text is its elements' text joined by blank lines: a TITLE/PARAGRAPH contributes its text, an IMAGE/CHART its description, and a TABLE its LLM summary if it has one, otherwise its raw markdown (`chunking/text.py`).
2. **Parents and children.** A section becomes a *parent* chunk (split further, without overlap, if it exceeds 8,000 characters); each parent is cut into ~200-character *children* with 20 characters of overlap, preferring paragraph, then line, then word boundaries. Only children are searched; the matched child's parent supplies the text the generator reads (§5, §10).
3. **Snapshots.** Each chunk keeps a `ChunkElement` snapshot of its source elements, including a 512 px thumbnail for pictures and charts that have bytes, so the UI can render a real table or picture instead of flattened text.
4. **IDs.** A chunk's id hashes its document id, the strategy, its position and its text (§5, §12).

**What that means for a spreadsheet — measured, not assumed.** CSV and Excel produce no title elements, so the *whole file is one section*. A 600-row CSV becomes 20 batch elements, then 4 parents (7,514 / 7,624 / 7,624 / 2,540 characters), then 140 children averaging 180 characters. Rows stay whole — the child splitter prefers line breaks, and none of the 140 children ends mid-row — but only 20 of the 140 (the first child of each batch) contain the header row; the other 120 are rows with no column names and rely on their parent for context. Batching therefore guarantees that each *batch* is self-describing, not that each *search hit* is.

### Which ingestion steps call an LLM

- **Vision caption:** one call per picture, in every format that has pictures.
- **Excel chart description:** one text-LLM call per native chart. (PPTX charts: none.)
- **Table summary** (`summarize_table()`): one call per table, so one per 30-row batch for CSV/Excel — **but only when `parse_document(..., summarize_tables=True)`, and nothing sets that (open defect 1 below).**

Every one of these fails soft: with no provider configured or a failed call, ingestion continues with a placeholder description or no summary.

### Open defects in this path

Found while writing this section, by running the code rather than reading it. Nothing has been changed for either yet.

1. **Table summaries are never generated in production.** `summarize_tables` defaults to `False` and no caller sets it — `POST /ingest`, `run_eval.py`, `run_expert_eval.py` and every demo call `parse_document(path)` — so `Element.table_summary` is always `None`, `element_text()` always falls back to the raw markdown, and the §18 change (embed the summary, show the generator the raw table) is implemented and unit-tested but inert. Turning it on costs one LLM call per table at ingest time (per 30-row batch for spreadsheets) and changes retrieval behaviour, so it wants a deliberate decision: a setting, and re-ingesting existing documents.
2. **The generator can receive an entire large spreadsheet per hit.** Measured on the 600-row CSV above: one hit on a parent holding 7,514 characters (about 3,000 tokens) makes the generator's context about 25,300 characters (about 9,980 tokens), against a 2,000-token budget. The mechanism and the candidate fixes are in §18.

## 5. Chunking

Five strategies live behind one `Chunker` interface: fixed-size, recursive character, semantic (embedding-similarity boundary detection), structure-aware (splits on document structure — headings, sections), and parent-child (structure-aware "parent" sections, each further split into smaller "child" pieces via `RecursiveCharacterTextSplitter`).

### Content-addressed chunk IDs

```
chunk_id = f"{doc_id}::{strategy}::{index}::{sha256(chunk_text)[:10]}"
```

Not purely positional (`doc_id::strategy::index`) — a hash of the chunk's *own text* is baked in. This single design choice is what makes several other things possible:

- **Idempotent re-ingestion**: unchanged text at the same position re-hashes to the same ID, so re-upserting is a no-op at the storage level, not a duplicate.
- **Chunk-level diffing on edits** (see [§12](#12-document-identity--incremental-re-ingestion)): a changed chunk gets a *new* ID; an unchanged one doesn't — the ID itself carries the information needed to tell "this changed" from "this is stale but identical," without diffing raw text at ingest time.

**Why `doc_id` has to be part of the hash, not just the text**: if `chunk_id` were `hash(text)` alone, two *different* documents that happen to share identical text (a boilerplate disclaimer, a repeated section header, common code) would collide into the *same* stored point. Whichever document was ingested most recently would silently win the citation metadata for that chunk, and deleting one document's stale chunks (an edit's cleanup step) could delete a completely unrelated document's copy of that same text. Scoping the ID to `doc_id` avoids this at the cost of never deduplicating storage across documents that happen to share content — a trade-off judged appropriate at this project's scale (see [§16](#16-known-limitations-named-on-purpose) for the fuller architecture that *would* dedupe across documents, and why it wasn't built).

### Parent-child retrieval

Children (small, ~200-character pieces) are what's actually searched — precise matching. Parents (the full section) are marked `is_parent=True` and excluded from search **natively at the store level** (a Qdrant payload filter, an Elasticsearch `bool.must_not`) — not a post-hoc application-level filter, so there's no way for a parent to leak into results by a caller forgetting to filter. On a matched child, `resolve_parent_context()` swaps the child's *text* for its parent's full text (more context for the LLM) while every other field — `chunk_id`, `source`, `pages` — keeps pointing at the child, so citations stay precise even though the model saw the fuller paragraph. If two different children of the *same* parent both rank in the top-k, only the higher-ranked one survives resolution — otherwise the LLM would see that parent's text twice for zero new information.

## 6. Embeddings

Multi-vector pattern: the raw content (text, image bytes) is kept for display; a *text projection* is what actually gets embedded and searched (a vision caption stands in for an image, a markdown rendering stands in for a table). Same embedding pipeline for every modality — nothing downstream needs to know a chunk originated from an image.

`ModelMismatchError`: `Qdrant.search()` compares the query vector's `model_id` against what's actually stored before searching. Dimension matching alone (which Qdrant already enforces) isn't sufficient — two different models can share a dimension count while encoding meaning in incompatible vector spaces, which would return confident-looking, *meaningless* results with no error at all otherwise.

## 7. Vector store — Qdrant

### How HNSW indexing actually works

Qdrant's approximate-nearest-neighbor index is a **Hierarchical Navigable Small World** graph — points connected into a multi-layer graph, top layers sparse with long-range links (like an express lane), the bottom layer dense with short-range links to every point. A search starts at the top layer, greedily walks toward the query vector until no closer neighbor exists at that layer, drops down one layer, and repeats — arriving at layer 0 already close to the true answer, then does a final local search there. This avoids a full linear scan (`O(n)`) in favor of something closer to `O(log n)`, at the cost of being *approximate* — it can miss the true nearest neighbor, traded for large speedups at scale.

Three parameters control the recall/speed/memory trade-off directly:

| Parameter | What it controls | Effect |
|---|---|---|
| `m` | max connections per node | higher → better recall, more memory |
| `ef_construct` | candidates considered while *building* the graph | higher → better graph quality, slower build |
| `ef_search` | candidates considered at *query* time | higher → better recall, slower query, exposed **per-call** (no rebuild needed to tune it) |

### Blue-green collection versioning

`collection_name` is a Qdrant **alias**, not a physical collection — `search()` always reads through it. `create_collection()` builds a new, uniquely-named physical collection *without* touching the alias; `publish()` atomically repoints the alias at the new collection and removes the old one. A production pipeline that instead deleted-and-rebuilt the live collection in place would have no rollback if the new version turned out broken, and no way to diff what changed to debug it — this makes that structurally impossible, since the previous version stays fully intact and queryable right up until the atomic cutover. `ensure_ready()` is the idempotent version used at service startup: create + publish an empty collection only if none exists yet, never touching an already-live one — safe to call on every boot.

Point IDs are a UUID5 hash of the human-readable `chunk_id` (Qdrant requires an int or UUID, not an arbitrary string) — deterministic, so re-upserting the same `chunk_id` updates the same point rather than creating a duplicate. The original readable `chunk_id` is kept in the payload for citation/debugging.

### Payload indexes

A *filtered* search (matching on a payload field, not just vector similarity) needs an explicit **payload index** on that field, or the query degrades from a fast, correct operation to a slow, potentially *lossy* one — not merely slower. HNSW's greedy graph walk was built assuming every point is reachable; a filter condition evaluated per-candidate *during* that walk can reject everything the walk encounters next, leaving it nowhere legal to hop and terminating before it ever reaches matches that genuinely exist elsewhere in the graph. An indexed field gets two things instead: extra graph links that keep the *filtered subset* connected, and a cardinality estimate Qdrant uses to fall back to exact brute-force search once the filter is selective enough. So a payload index is a **correctness precondition for filtering**, not a speed optimization — this became load-bearing once document-scoped retrieval (§10) needed to filter on `doc_id`.

`is_parent` had run unindexed on *every single search* since parent exclusion (above) was built — filtered, just never indexed. Indexes are created in two places, deliberately, because of blue-green versioning: inside `create_collection()`, against the new physical collection, before a single point is written, so a version the alias later cuts over to is never briefly live-but-unindexed; and inside `ensure_ready()`, against the currently-live alias, so a collection that predates a given index gets healed at the next service restart — no rebuild, no re-embedding. Index-creation failures are caught and logged, not raised: `ensure_ready()` runs during service startup, and a schema conflict on an old collection taking the whole API down at boot would be a strictly worse outcome than one field silently falling back to unindexed (slower, still correct) filtering.

## 8. Keyword store — Elasticsearch

### How the inverted index + BM25 actually work

A forward index maps document → terms; an **inverted index** maps *term* → the list of documents containing it (a "postings list"), which is what makes a keyword search fast — looking up "GPU" jumps straight to the documents containing it instead of scanning the whole corpus.

**BM25** ranks the matching documents by combining three signals:
- **Term frequency**, saturating (not linear) — the 10th occurrence of a term in a document adds much less score than the 2nd, controlled by a `k1` parameter.
- **Inverse document frequency** — a term that appears in *most* documents (like "the") is a weak signal; a term appearing in only a few documents is a strong, discriminating one.
- **Length normalization** — a term appearing once in a 20-word chunk is more significant than once in a 2,000-word one, controlled by a `b` parameter.

**Why keyword search still matters next to embeddings**: exact identifiers, part numbers, and error codes are exactly what embedding similarity blurs (an embedding model represents *meaning*, and "ERR-4471" doesn't have meaning to blur toward) — BM25 matches the literal token.

**Analyzer choice**: the `standard` analyzer (lowercasing + whitespace/punctuation tokenization, *no stemming*) was chosen explicitly over Elasticsearch's fancier options — stemming risks mangling exact codes/identifiers ("CVE-2024-12345") in exchange for generalizing prose forms ("test"/"tests"/"testing") this corpus doesn't especially need. Known, documented, *not-yet-fixed* gap: the standard tokenizer splits on hyphens, so `"internal-llama-70b"` indexes as three separate tokens — still matches on any of them, but blurs exact-phrase precision. The real fix (a second, un-analyzed `keyword`-typed field for exact matching) was named and deliberately deferred, not missed.

`chunk.id` is used directly as the Elasticsearch `_id` — no UUID conversion needed here, unlike Qdrant, since ES document IDs accept arbitrary strings natively.

## 9. Hybrid indexing & consistency

`HybridIndexer` coordinates writes to both stores so "upsert into Qdrant, then index into Elasticsearch" isn't two separate, uncoordinated calls scattered through the codebase. **Not** true cross-database atomicity — Qdrant and Elasticsearch share no transaction mechanism, and building one (a single source-of-truth store both stores sync from independently, the way real search infrastructure eventually solves this) was judged disproportionate for this project's scale. What it *does* give: a persistent failure on the second write raises `IndexConsistencyError` carrying exactly which `chunk_id`s are now inconsistent, rather than a silent gap discovered later via a confusing search result — plus `check_consistency()`, which compares `list_chunk_ids()` between both stores independently to catch drift from *any* cause (a failed write, a deletion that only touched one store, manual intervention).

`delete()` mirrors `index()`'s ordering and error-handling exactly, for the same reason: vector store first, keyword store second, so a persistent failure on the second step is reported precisely instead of silently leaving one store cleaned and the other not.

## 10. Retrieval

One `Retriever.retrieve(query, method, top_k, ...)` call, method selected per-query:

- **Cosine** — a thin wrapper over the vector store's own similarity search.
- **BM25** — a thin wrapper over the keyword store.
- **MMR (Maximal Marginal Relevance)** — trades relevance against redundancy:

  ```
  MMR = argmax_{d ∈ R∖S} [ λ·Sim(d, query) − (1−λ)·max_{s∈S} Sim(d, s) ]
  ```

  Greedy iterative selection: repeatedly pick the candidate maximizing relevance minus similarity-to-already-selected. `λ=1` degenerates to pure relevance ranking (identical to plain cosine); low `λ` actively prefers a diverse set over a cluster of near-duplicates, even at some cost to raw relevance. Requires candidate vectors (`with_vectors=True`) to compute the redundancy term.

- **Hybrid (Reciprocal Rank Fusion)** — fuses cosine and BM25 rankings:

  ```
  RRF_score(d) = Σ_r 1 / (k + rank_r(d))
  ```

  summed over each ranking method `r` that returned `d`, `k=60` a standard damping constant. Fused by **rank position**, not raw score — a BM25 score (unbounded, corpus-dependent) and a cosine score (bounded, model-dependent) aren't measuring comparable things and can't be meaningfully rescaled onto each other, but "ranked #1" means the same thing regardless of which method produced that ranking. This is the real, practical answer to "how do you combine two different scoring systems."

- **Reranking** — an *orthogonal* `rerank: bool` flag applicable to any method above, not a fifth method: retrieve a broader candidate pool, then re-score it with a cross-encoder (`CrossEncoderReranker`, local `sentence-transformers`) before cutting to `top_k`. Cross-encoders score a (query, document) pair *jointly* — much more accurate than comparing two independently-computed embeddings, but too expensive to run over an entire corpus, hence "retrieve broad, rerank down" rather than "rerank everything." Only the local cross-encoder path was built; a hosted reranker (Cohere/Voyage-style) was explicitly *not*, for lack of credentials to test against — a scoped decision, not an oversight.

Since `is_parent=True` chunks are excluded from search **natively at the store level** (§5), reranking *always* operates on precise child text, never parent text — this became true unconditionally once that store-level filter was in place, not just "usually true because children tend to rank higher."

### Document-scoped filtering: a native store query, not a post-retrieval cut

`retrieve(..., doc_ids=[...])` used to fetch a widened candidate pool by similarity first, then filter it down to the requested documents in a Python list comprehension *afterward*. That has a real failure mode, not just a scaling one: the chunks that satisfy the filter can rank arbitrarily low in the *unfiltered* similarity order — if they fall outside whatever pool got fetched, they're gone before the filter ever runs, and the call returns fewer results than exist, or none. A test makes this concrete: a corpus where the two chunks matching the requested `doc_id` are deliberately the *least* similar to the query among the whole corpus — ranked outside any candidate pool a plain similarity search would fetch — proves the old design would have returned nothing for them, and the new one still finds them, because filtering now happens *during* the search itself.

The mechanism: `SearchFilter` (`stores/filters.py`) is a small backend-neutral shape — `any_of: dict[str, list[str]]`, fields AND together, each field's own value list ORs — that each store translates into its own real query language: `VectorStore` builds a Qdrant `FieldCondition(match=MatchAny(...))`, ANDed with the pre-existing parent-exclusion condition in exactly one place (`_build_query_filter()`) so a caller-supplied filter can only ever *add* a constraint, never replace the one the store itself enforces; `KeywordStore` puts the equivalent `terms` clause in Elasticsearch's `bool.filter`, not `bool.must` — filter context doesn't contribute to the BM25 relevance score and is eligible for ES's filter cache, both of which matter once a filter runs on *every* query rather than occasionally. `doc_ids` stays the public parameter on `Retriever.retrieve()` — internally it's just sugar that builds one `SearchFilter` and threads it into whichever store call the chosen `method` makes, so a hybrid RRF fusion, an MMR selection, and a plain cosine search all get identical document scoping instead of three separate implementations of it.

One correctness detail worth stating precisely: `doc_ids=[]` (an explicit empty list) and `doc_ids=None` (the parameter omitted) are *not* the same thing, and the translation preserves that distinction on purpose — `None` means no filter at all, `[]` means "match no document," carried through as `MatchAny(any=[])`/`terms: {field: []}`, both of which correctly match nothing rather than silently degrading to "everything."

Deliberately still not built, because nothing yet needs it: `SearchFilter` has no `none_of`. It does have `merge()` (§13) — added once a real second filter existed to compose against (the mandatory access-control clause) — and, since the user-facing filter panel below, a `date_range` condition too, both added once an actual caller needed them rather than guessed at ahead of one.

### Recency without a declared replacement

§12 covers a document explicitly replacing another. This is the other half: two documents that disagree with nobody having said so. `_apply_recency_and_collapse()` runs on the full candidate pool, after fusion or reranking, before the `top_k` cut — a small, bounded, multiplicative boost toward a more recent `effective_from` (`Settings.recency_tilt_weight`, default a 10% maximum, decaying with `Settings.recency_half_life_days`, default ~6 months), plus collapsing multiple results from one `doc_family_id` down to the highest version present. Both read `version`/`doc_family_id`/`effective_from`/`status` straight off the chunk's stored payload (now on `SearchResult` itself), not a database lookup — a ranking nudge being briefly stale is a quality issue, unlike the access-control checks (§13), which re-verify against sqlite because being stale there is a leak.

**A real design mistake, found by running the existing test suite, not by reasoning it through first.** The first implementation re-scored and re-sorted every result by `.score` regardless of method. That is only sound when `.score` genuinely reflects the order results are already in — true for cosine, BM25, and RRF fusion (which overwrites `.score` with the fused value), but **not** true for MMR or after reranking. MMR's own code says so directly (`_mmr`: "`score` here is already the candidate's raw relevance — MMR never rewrites it") — it picks the second and later slots for a mix of relevance *and* diversity, so raw score does not track its own selection order. A cross-encoder reranker is worse: its `rerank()` method takes only `(query, texts)` — it never receives `.score` at all, so nothing about it can be "consistent with" a score-based resort. Applying the tilt's resort after either one didn't nudge their judgment, it silently overwrote it, and two pre-existing tests (`test_mmr_with_low_lambda_prefers_diversity...`, `test_rerank_reorders_results_via_the_reranker`) caught it immediately — with the recency weight at zero effect (no chunk in either test carries an `effective_from`), simply because "sort by `.score`" and "the order MMR/rerank actually produced" are different orderings on their own, independent of any tilt at all.

The fix: the tilt's resort only runs when `method != MMR and not rerank`; family collapse always runs, whatever produced the order, because removing an item can never disturb the relative order of the ones that remain. **A real, named cost**: the recency nudge does not apply once a result has been reranked, so on the highest-precision retrieval path (cross-encoder reranking), recency stops being able to break a tie. A locally-bounded reordering (swap only adjacent, low-confidence pairs) was considered and rejected for this phase — with as few as two candidates, a small positional swap and a magnitude-aware tiebreak are indistinguishable, so it could not be built without also losing the "never override a real relevance gap" guarantee the score-based version keeps for the other three methods.

A second mistake, caught the same way: the first version of family collapse fell back to grouping by `doc_id` when `doc_family_id` was absent. That is wrong independent of any test fixture's habits — two chunks that share a `doc_id` are two *passages* of the same document (different pages or sections), not duplicates of each other, and collapsing by that fallback silently dropped every chunk of a document but one. Collapse now groups by `doc_family_id` only; a chunk with no family tag is left alone entirely, compared against nothing, the same "no signal, no penalty" rule the tilt itself uses for a missing `effective_from`.

A third, found only once the *whole* suite ran, not just the tests written for this phase: family collapse and §12's `include_superseded` flag are in direct tension. Collapse exists to keep exactly one version of a family in a normal answer; `include_superseded` exists to show every version on request. Left unconditional, collapse silently defeated the flag — a caller who explicitly asked for history still got only the newest version back, with every older one removed before they ever saw it, and two of §12's own lineage tests (written before this phase existed) caught it precisely because they checked what `include_superseded=True` actually returned. `retrieve()` gained a `collapse_families` parameter (default `True`); `ScopedRetriever` sets it to `not include_superseded`, so the two features compose correctly — asking for history turns off exactly the mechanism that would have hidden it, and nothing else.

The model is told what it's looking at, not just handed re-ordered chunks: `format_context_block()` appends version/status/date to a citation only when there's something to say (silent for a plain, untagged, current, version-1 document, so an ordinary citation looks exactly as it always has). One rule, `CONFLICT_RESOLUTION_RULE` (`prompt.py`), is embedded verbatim in both `RagChain`'s and `AgentChain`'s system prompts — the two already duplicate three other rules by hand (§11), and the module docstring names that as the real drift risk; importing one shared string for this new rule is what actually keeps it from drifting the way the others could.

### A user-facing filter: tags, author, and a date range

`SearchFilter` gained a `date_range: dict[str, tuple[str, str]]` field (field → inclusive `(from, to)` ISO date strings) alongside `any_of`, once a real caller for it existed: the frontend's "Filters" panel (§14). `merge()` narrows a `date_range` field present in more than one filter the same way it already narrowed `any_of` — to the *overlap* (later of the two `from`s, earlier of the two `to`s) — so a caller-supplied date range composes with the mandatory security/lifecycle filters exactly like `any_of` does: it can only shrink what's already allowed, never widen past it. Both stores translate it natively: Qdrant gets a `FieldCondition(range=DatetimeRange(gte=..., lte=...))` (pydantic coerces a bare `"YYYY-MM-DD"` string to midnight on both the query bound and the stored value, so the inclusive boundary date matches correctly without any manual end-of-day adjustment); Elasticsearch gets a `{"range": {field: {"gte": ..., "lte": ...}}}` filter clause.

`doc_date` is the field this actually filters on (not `effective_from`, which stays specialized for lineage/recency) — the more intuitive "when is this document from" for a general corpus filter. Two backing changes were needed for it to be a real range-queryable field rather than an exact-match one: a new Qdrant `DATETIME` payload index (alongside new `KEYWORD` indexes for `tags`/`author`, the other two filterable dimensions), and Elasticsearch's `doc_date` mapping changed from `keyword` to a real `date` type. That second change has a real cost the `keyword` mapping had deliberately avoided: a `date`-typed field rejects a non-ISO-parseable value at *index* time, whereas `keyword` would have just stored whatever string arrived. Closed the same way `classification`'s required-field check already does — `DocumentMetadata.doc_date` gained a pydantic validator (`date.fromisoformat`) so a malformed value is rejected at the API boundary (a 422 on `/ingest` or `PATCH`), not three layers down as a confusing bulk-indexing failure inside `HybridIndexer.index()`.

The API-facing shape is `MetadataFilterRequest` (`api/schemas.py`): `tags`/`author`/`date_from`/`date_to`, all optional, converted to a `SearchFilter` via `to_search_filter()` — an entirely-empty request becomes `None` (no constraint at all), and an open-ended date bound (only `date_from` or only `date_to` set) widens to the full possible range on the missing side (`"0000-01-01"`/`"9999-12-31"`) rather than requiring the frontend to already know the corpus's actual min/max `doc_date` just to narrow one side. `QueryRequest.metadata_filter` is threaded through exactly like the existing `doc_ids`/`include_superseded`: a **request-level** argument set once by the human asking the question, passed as a fixed parameter into `AgentChain.answer()` and from there into every `retrieve()` call for that turn — never something the model's own tool-call arguments could set or widen, for the identical reason the mandatory security filter itself sits below the agent (§13): a prompt-injected document has no path to it.

### Making a chunk's own metadata, and a query's own filter, visible in Langfuse

`SearchResult` carried lineage fields (`version`/`doc_family_id`/`effective_from`/`status`) but nothing from the *rest* of `DocumentMetadata` — a retrieval span in Langfuse showed a chunk's score and a text preview, never what it actually IS (its tags, who wrote it, when, its confidentiality level). Closed the same way the lineage fields were: `SearchResult` gained `tags`/`author`/`doc_date`/`classification`/`private`, populated in both stores' `search()` straight off the same stored payload, and folded into `_summarize_results()` (`retrieval/retriever.py`) — the dict that already becomes every retrieval span's `output`. Deliberately for **observability only**: `classification`/`private` on a `SearchResult` are never a second place to decide who may see a chunk — `ScopedRetriever`'s mandatory filter and sqlite post-check (§13) already settled that before a result ever reaches here.

The other half — which filter, if any, narrowed a given question's retrieval — needed `traced_query()` (`tracing.py`) to accept the caller's `metadata_filter` and attach it to the trace's own metadata (alongside the existing `query_id`), so it's visible at a glance on the trace itself rather than requiring a cross-reference back to the original request. `routers/query.py` builds this from `request.metadata_filter.model_dump()` once per request and passes it straight through.

## 11. Generation

### The chain(s)

Two generation paths share the same building blocks (`assemble_context`, `parse_answer`, the grounding rules baked into each one's system prompt). `RagChain` is a pure single-shot retrieve → generate → parse pipeline, built with LangChain's LCEL (`RunnableLambda` steps composed via `|`) used purely as an **orchestration layer** — the actual model call still goes through `get_llm()` from the providers factory, so "same chain runs against a local OpenAI key and an internal company LLM, no code change" stays exactly as true in generation as everywhere else. `AgentChain` (below) is the interactive path: a hand-rolled loop, not LCEL, since "call the model, maybe call a tool, maybe loop" isn't a fixed pipeline the way single-shot retrieve-then-generate is. LangChain's own model-wrapper classes (`ChatOpenAI` etc.) were deliberately not used in either, for the same vendor-coupling reason as [§3](#3-providers-layer). State threads through `RagChain` as a dict, each step adding a key — the standard LCEL pattern for carrying auxiliary data (the retrieved context, needed again after the LLM call to map citation markers back to real metadata) alongside the main value.

### Agentic tool-calling

The original design rewrote a follow-up question into a standalone one with a separate LLM call, then always ran exactly one retrieve + one generate. Replaced with a real agent: the LLM gets one tool, `search_knowledge_base(query)`, and decides for itself — across up to `max_tool_rounds` rounds — how many searches a message needs. This is what turns "how does X compare to Y, and what's Z" into two targeted retrievals instead of one vague one, and is what let the old rewrite step (and its "Conversation so far:" text-flattening trick) be deleted outright: the model now sees real `user`/`assistant` messages for prior turns and decides for itself whether/how to search again for a follow-up.

**Rounds vs. calls**: `max_tool_rounds` caps *rounds* (one LLM turn), not raw search count — a single round can include more than one *parallel* tool call (observed live: a compound question triggered two `search_knowledge_base` calls in the same round, not two rounds). The system prompt names this distinction explicitly rather than saying "N searches," because an earlier draft's "N searches, comfortably enough for a two-question decomposition" phrasing was two bugs at once — it undercounted real capacity (parallel calls aren't one-per-round) and hardcoded an editorial claim that would go stale the moment the round default changed.

**Search-before-refusal is a state-machine invariant, not only a prompt rule**: exposing a tool to an LLM makes it available; it does not guarantee the model will call it. Observed live, the model sometimes obeyed the grounding rule too early and returned the exact refusal sentence before performing any search. It could also stop after one poorly phrased search returned no chunks, treating retrieval failure as proof that the corpus lacked the answer. The prompt now states an explicit protocol: search before refusing, and reformulate once after an empty result. Application code enforces the same boundary: a refusal before any search is replaced by a search using the original question; a refusal while the accumulated context is still empty triggers one additional model turn with `tool_choice="required"` and an instruction to use materially different terms. A refusal after nonempty evidence is accepted, because the retrieved passages may genuinely omit the requested fact. The forced reformulation is allowed only once and still consumes the existing `max_tool_rounds` budget, preventing an unproductive model from looping forever. This deliberately combines probabilistic guidance (the prompt helps the model choose a better query) with deterministic control flow (Python decides when refusal is legal).

**Append-only citation ledger**: `⟦N⟧` markers are resolved *positionally* (`parse_answer()` maps marker N to `context[N-1]`), so a marker's meaning must never change once shown to the model. Chunks accumulate across rounds in a strictly append-only list — a chunk already seen (two sub-questions surfacing the same passage) keeps its original marker rather than being renumbered. Re-sorting the ledger by relevance before the final answer, an intuitive-sounding alternative, would silently break this: the model commits to a marker number in its own generated text the moment a tool result shows it one, and renumbering afterward would resolve that marker to a *different* chunk than the one actually cited.

**Clarifying questions (human-in-the-loop)**: when a request has no resolvable referent (an unresolved pronoun, a follow-up with nothing to anchor to), the model is instructed to ask instead of guessing or searching speculatively — reusing the same exact-sentinel idiom the refusal text already used (`"CLARIFYING QUESTION: "`, checked as a literal prefix, never inferred from free-form text). This needed no new session-state plumbing: the user's reply is just their next chat message, threaded through `history` like any other follow-up. Getting a reliable trigger phrase took live iteration — "how does it compare to the baseline?" didn't trigger it at all (the model tried four search rephrasings for "baseline" before giving up and refusing, since a plausible-sounding technical term reads as worth searching for, not as unresolvable), while "can you compare it with the one we discussed earlier?" reliably did, since referencing nonexistent prior discussion is a much stronger, less searchable signal of missing context.

**Two real gaps found only by testing against a live model, never surfaced by the mocked test suite**: (1) `gpt-4o-mini` sometimes substituted an adjacent-but-different fact (P95 when asked for P99) instead of refusing, despite the prompt saying not to — fixed by naming the failure mode explicitly in the refusal rule ("even if a related but DIFFERENT fact is present, do not substitute"). (2) it sometimes cited using its own trained-in browsing-citation format (`【N†source】`) instead of the requested `⟦N⟧`, despite the prompt explicitly forbidding it — and kept doing so in roughly 1 of 3 live attempts even after that instruction was strengthened. Prompting narrowed but did not close this gap, so `parse_answer()` now normalizes the one variant actually observed back to `⟦N⟧` before parsing, rather than relying on compliance alone — the same "prompted, not enforced" lesson recurring at two different layers of the same system.

**System prompt structure**: organized into explicit `##`-headed sections (Role, The Corpus, Searching, When To Ask Instead Of Searching, Grounding And Refusal, Citation Format, Handling Document Content Safely, Conversation Context, Examples) rather than one flat rules list, plus a few-shot Examples section built on a deliberately *unrelated* fictional domain (an employee handbook). A few-shot example sharing content with the actual test/demo corpus would risk the model pattern-matching toward that specific content rather than generalizing the underlying rule — making tests look artificially better than the rule actually is.

### Context assembly

Token-budgeted, **greedy fill by rank**: include results in ranked order until the next one would exceed the budget, then stop — dropping the *tail* of the ranking (lower-relevance results), never truncating an individual chunk's text (a half-sentence of context is worse than one fewer whole chunk). Always includes the top result even if it alone exceeds budget — an empty context defeats the point of the guardrail below.

### Citations and the guardrail

The system prompt instructs the model to answer *only* from the numbered context blocks, to refuse with an exact, matchable sentence if the answer isn't present, and to cite claims inline using a distinctive marker: `⟦1⟧`, not `[1]`. That choice mattered in practice, not just in theory — plain `[N]` collides with bracketed numbers that occur naturally in source documents (footnotes, step lists, array indices) *and* in a model's own enumerated-list writing style, and either would be misread as a citation by a naive `\[(\d+)\]` regex. `⟦…⟧` is distinctive enough that it only appears when the prompt put it there.

Citations are never trusted from the model's own recall of filenames or page numbers — `parse_answer()` only extracts *which numbered marker* was used, then looks up the real `chunk_id`/`source`/`pages` from the context **we** already built. The model's job is picking which block is relevant; the mapping back to real metadata is entirely programmatic.

**Prompt injection**: context blocks are framed explicitly as *data to read*, not instructions to obey — a mitigation, not an elimination (an LLM reliably distinguishing "instructions" from "data that looks like instructions" isn't a solved problem). The limiter on blast radius is architectural, not behavioral, and it changed with the agent: `AgentChain` *does* let the model trigger a real tool call now (unlike the plain `generate()` path `RagChain` uses), but the only tool that exists is a read-only search over the corpus itself — so a successful injection can at most steer *what gets searched next*, never perform a side-effecting action. That property has to be judged fresh against any future tool added to the agent, not assumed to carry forward automatically.

## 12. Document identity & incremental re-ingestion

This is the area with the most iteration, because it surfaced a real tension worth stating precisely: a *single* identity value cannot simultaneously be (a) stable across a file being renamed, and (b) stable across a file's content being edited — because "derived from content" (needed for (a) without relying on the filename) definitionally changes the moment content changes (breaking (b)), and "not derived from content" (needed for (b)) has nothing to anchor renaming-invariance to.

The resolution actually shipped:

- **`doc_id` is a hash of (uploader, filename)** — deliberately *not* a content hash, and, since access control, not the bare filename either (see "Whose document is it?" below). This is what makes chunk-level diffing possible: `chunk_id` embeds `doc_id` (§5), so a stable `doc_id` across an edit means only the chunks whose *text* actually changed get new IDs — the rest are recognized as already correctly stored and skipped, not blindly re-embedded. Editing one word in a 34-chunk sample document, verified directly: 29 chunks untouched, 5 re-embedded, 5 stale ones actually deleted — not 34 orphaned and 34 redone (an earlier, content-hash-based `doc_id` design had exactly that failure mode, caught and fixed).
- **`content_hash = sha256(bytes)`**, tracked separately in the `documents` table, purely to detect "nothing changed" (an exact re-upload under the *same* filename) without redoing any work to find out.
- **A global content-hash check**, independent of `doc_id`: before parsing anything, check whether this exact content already exists *anywhere* in the corpus, under *any* filename. This is what actually solved a real bug — the same file uploaded once via a single-file picker (reports a bare filename) and once via a native folder picker (reports a path-prefixed name, via the browser's `webkitRelativePath`) wasn't recognized as the same document, because the two upload paths produced two different filename strings and therefore two different `doc_id`s. Rather than normalizing filenames (guessing which of several possible naming quirks — a path prefix, Unicode normalization — was responsible in a given case), checking content globally sidesteps the question entirely.

**Named trade-off, not a bug**: renaming a file with *unchanged* content is no longer deduplicated as "the same document" the way it briefly was in an earlier iteration — a rename is a new `doc_id`. Two genuinely different files that happen to share a leaf filename (`notes.md` in two unrelated folders) will collide into one `doc_id` if the *same person* ingests both. Deletion of orphaned chunks on an edit (`Chunk_ids present before, absent in the new chunking`) is computed by filtering `list_chunk_ids()` for the `doc_id::` prefix every chunk_id already carries — no separate tracking table needed, since the scoping is already baked into the ID itself.

The fully general fix — content-addressed chunk *storage* decoupled from document *membership*, the way git separates content-addressed blobs from the tree/commit structure that tracks which blob belongs to which path — would get every property at once (including deduplicating identical content *across* unrelated documents), at the cost of a real architecture change: a many-to-many storage model instead of one-point-per-chunk, reference-counted deletion, and citation logic that can attribute a chunk to more than one document. Named explicitly as the "textbook correct" answer and explicitly not built, as disproportionate to this project's single-user scale.

**A payload identity bug, found once document-scoped retrieval actually needed `doc_id` to be correct.** `ChunkMetadata.source_file` served two different purposes at two different points in the ingest pipeline: the stable `doc_id` while chunk IDs were being computed (so `chunk_id` — above — hashes it in), then swapped back to the human-readable filename immediately after, purely for citation display. The *payload* written to both stores read `doc_id` from that same field, after the swap — so the value actually stored as `doc_id` was silently the **filename**, identical to the `source` field sitting right next to it, while `GET /documents`, `DELETE /documents/{doc_id}`, and `IngestResponse` all handed out `sha256(filename)`. A `doc_ids` filter (§10) passed the real id and matched nothing.

The fix adds `doc_id` as its own field on `ChunkMetadata`, set in the identical loop that restores `source_file` to the filename, so the two values are tracked side by side rather than one silently overwriting the other in the payload — and the payload writers stop reading `source_file` for it, with deliberately **no `or source_file` fallback**: a fallback would let the bug resurrect itself silently for any write path that forgot to set the new field, rather than making a missing value visibly absent (`doc_id=""`). Because `doc_id` was always embedded as the *prefix* of `chunk_id` itself (`chunk_id.split("::", 1)[0]`), fixing already-stored data costs zero re-embeddings — a `set_payload`/bulk-update sweep (`scripts/backfill_doc_id.py`) recovers the correct value from data already there, the same "the ID already carries what you need" property that makes orphan-chunk deletion (above) cheap.

### Whose document is it? Identity had to include the uploader

With one user, "the same filename" and "the same document" were the same thing. With several, they aren't: two people's `README.md` are different documents, and under a filename-only `doc_id` the second upload would have hit the "existing document" path — replacing the first person's content, classification, and **owner** — a document takeover through nothing more than a filename collision. So `doc_id` is now a hash of the authenticated uploader *and* the filename (`routers/ingest.py`'s `_document_id`). The pair is JSON-encoded before hashing rather than joined with a separator, because a plain join is ambiguous — `("a:b", "c")` and `("a", "b:c")` would collide — and this is the one value that decides whether two uploads are the same document. Nothing else needed to change: `chunk_id` already derives from `doc_id`, so chunks, orphan cleanup, and filtering all follow. It also meant no migration, since the database held no documents when this was done; a deployment with existing data would need its documents re-keyed.

`Database.upsert_document` independently refuses to overwrite a row its caller doesn't own, so a future change that reintroduced a collision would produce a rejected upload rather than a takeover.

### Document metadata: where tags live, and why they're mutable without a re-embed

`metadata.DocumentMetadata` is a new, deliberately neutral top-level module — not under `api/` or `stores/` — holding the tags a *document* carries: `classification` (public/c1/c2/c3, cumulative, **required with no default**), `private`, `owner`, `author`, `doc_date`, `data_type`, `tags`. Neutral because both sides need it without creating a layering violation: `api/db.py` (the sqlite `documents` table, the source of truth) and `stores/*` (the denormalized copy on every chunk's payload, for filtering without a join) both import it, and a store must never depend on `api/` (§1's ports/adapters boundary).

**Required means required, at every layer, not just documented as a convention.** `classification` has no pydantic default, so `DocumentMetadata()` without it simply cannot be constructed. `POST /ingest`'s `metadata_json` Form field has no default either, so a request that omits it entirely never reaches application code — FastAPI itself returns 422. A request that sends the field but with an incomplete or invalid document (missing/misspelled classification) is caught explicitly and mapped to a 400. The reasoning: a document with no classification is one nobody can reason about access for, and silently defaulting it to something "safe-looking" is exactly the kind of swallowed requirement that turns into a leak or a lockout nobody can diagnose from the outside — so it's designed to be structurally impossible to skip, not merely discouraged.

**Deliberately NOT put on `ChunkMetadata`.** Two independent reasons: (1) every chunking strategy builds `ChunkMetadata` by hand — `ParentChildChunker` copies its fields one by one into every child chunk (§5) — so a new field added there would be *silently dropped* on exactly the chunks that get searched, no type error, nothing visible; (2) document metadata is mutable *after* chunking (an owner corrects the author, someone flips a document to private), and putting it on `ChunkMetadata` would imply re-chunking just to change a tag. Instead it rides one `doc_metadata: DocumentMetadata | None` argument through `HybridIndexer.index()` into both stores' payload writers (merged in by `DocumentMetadata.to_payload()`, the one place these field names are spelled for both backends), keeping every chunker untouched.

**The corollary — a metadata change must never require a re-embed — is what `set_document_metadata()` exists for.** Both stores gained this method: Qdrant's is a `set_payload` scoped to a `doc_id` filter (merging the given keys into whatever's already stored, not replacing the whole payload); Elasticsearch's is an `_update_by_query` with a script built from the given fields' own keys (so it can never drift out of sync with `DocumentMetadata`, and the keys — always drawn from that fixed schema, never arbitrary caller input — pose no injection risk being interpolated into the script source; only the values travel through `params`). `HybridIndexer.set_document_metadata()` coordinates both, same ordering/error-handling rationale as `index()`/`delete()` (§9). This single mechanism serves two callers: a sweep at the end of every successful `/ingest` (covering chunks an edit's diff left untouched — those were never re-embedded, so they'd otherwise still carry stale tags), and `PATCH /documents/{doc_id}` (a caller editing tags later, with no upload at all). Both funnel through one implementation, so they can't drift apart.

**Why re-uploading a file does NOT update its metadata.** `POST /ingest`'s `already_ingested` short-circuit (above) returns before touching anything, on purpose — whatever the new request's `metadata` says is discarded, not merged. `PATCH /documents/{doc_id}` is the only metadata-update path. This is a deliberate, named asymmetry: content changes through upload, tags change through PATCH, and conflating them would mean a re-upload silently overwriting a classification someone else had already reviewed and set.

**PATCH's partial-update semantics rely on `model_dump(exclude_unset=True)`, not on which fields are `None`.** `DocumentMetadataUpdate` has every field optional so a caller sends only what changed; distinguishing "the caller sent `private: false`" from "the caller didn't mention `private`" needs pydantic's own unset-tracking, not a `None` check — `private=False` is a legitimate value, not an omission.

### Version lineage: replacing a document without deleting it

Two documents that say opposite things — the 2025 policy and the 2026 one — used to both come back from a search, and the model picked one. Nothing said which was current. This subsection fixes the *declared* case: someone says "this replaces that". Two documents that contradict each other with nobody saying so is a different problem (recency and authority ranking, plus telling the model each source's date) and is not solved here.

**Explicit, never guessed.** `POST /ingest` takes an optional `supersedes_doc_id`. Inferring supersession from similar filenames or similar content would silently hide a document someone still needs, and hiding is exactly what supersession does — so the person uploading says so. It is a separate form field, not part of `metadata_json`, because it is an action ("do this to that document"), not a tag.

**Retire, don't delete.** The old version gets `status="superseded"` and an `effective_to` timestamp; its chunks stay in both stores, untouched and not re-embedded — retiring is a tag patch, the same mechanism as `PATCH /documents/{doc_id}`. That keeps the replacement undoable (`PATCH {"status": "current"}` restores it everywhere) and keeps history searchable on request; the cost is that retired versions occupy storage indefinitely, with no retention policy.

**What a document carries.** `status` (`current`/`superseded`), `doc_family_id` (the first version's `doc_id`, inherited by every replacement), `version` (the replaced document's version + 1), `effective_from` (uploader-supplied: when it takes force — distinct from `doc_date`, when it was written), and `effective_to` (set and cleared automatically with status). All of it lives on `DocumentMetadata` so it travels in the same `to_payload()` every write path sends. The lifecycle fields (`status`, `doc_family_id`, `version`, `effective_to`) are decided by the server: an upload's `metadata_json` cannot forge them, and PATCH lets an owner change only `status` and `effective_from`. Re-uploading the same filename stays an in-place edit and does **not** change the version — a "v3" with no v1 or v2 behind it would mislead; a version number only ever comes from an explicit replacement.

**Replacing needs the right to delete.** Replacing a document hides it from search, so it requires the same permission as deleting it (owner or admin): otherwise anyone could hide anyone's document by "replacing" it. A target the caller can't see is a 404, one they can see but don't own a 403, and a document replacing itself a 422 — all checked before anything is parsed or embedded, so a refused upload stores nothing. The cost is that team B cannot publish version 2 of team A's document; team A has to retire it.

**Order of operations.** The replacement is ingested and fully stored first; only then is the old version retired (catalogue first, being the authority, then the stores' copy). The other order would leave the old version hidden with nothing to replace it if the ingest failed part-way — a worse state than briefly showing both. If the store update fails after a good ingest, the upload still succeeds with a warning: the catalogue already says "superseded", search enforces that on its own, and repeating it is a `PATCH`. A duplicate upload that also asks to replace something changes nothing and says so in `ingest_warnings`.

**Search.** `ScopedRetriever` adds `status == "current"` to the store query by default, composed through `merge()` with the security filter so it can only narrow it. `include_superseded` on `/query` removes *only* that lifecycle clause: it never reveals a document the caller couldn't otherwise see. The post-check re-verifies status against the catalogue as well as visibility, so a store copy that hasn't caught up with a supersession cannot put a retired version back into an answer. A chunk with no `status` at all is treated as not current — the same fail-closed rule as classification.

### Rows from before classification existed

A document row written before classification was required has `classification = ''`. Parsing one raises, which is right for a single row — assigning it a classification would be a guess about access. But letting that propagate out of a *list* turned one old row into a 500 on `/documents` and `/metrics` for every user; this was found when a developer's real database, no longer empty, made both endpoints fail. Lists, counts and lookups now skip an unreadable row, log it at `ERROR` with what to do about it, and never assign it a classification: it stays invisible and unsearchable until it is re-ingested or backfilled. The simplest remedy for a handful of test documents is to wipe and re-ingest; such documents' chunks also predate the `doc_id` fix (§12), so they wouldn't match a `doc_id` filter anyway.

## 13. API layer

FastAPI, `async def` route handlers wrapping every blocking call (Qdrant/ES clients, `litellm`, local model inference) in `starlette.concurrency.run_in_threadpool` — without that, a single slow embedding call would block the entire event loop and serialize every other request behind it, silently defeating the point of declaring the endpoint `async` at all.

**Idempotent-ready ingestion** short-circuits on a known, unchanged `doc_id`+`content_hash` *before* touching the file — parsing, chunking, and embedding are skipped entirely, not merely deduplicated after the fact. `IngestResponse.status` distinguishes `"ingested"` / `"already_ingested"` / `"duplicate_content"` so a caller (and the frontend) can tell those apart instead of everything looking like a fresh ingest.

**`ensure_ready()` vs. blind recreation at boot**: Elasticsearch's `create_index()` is destructive (drops and recreates), so calling it unconditionally on every service startup would silently wipe a previously-indexed corpus on every restart. `ensure_ready()` checks existence first — create only if missing, otherwise a no-op — and is what's actually safe to call on every boot.

**Self-healing sqlite schema**: `CREATE TABLE IF NOT EXISTS` runs on *every* connection now, not once at `Database.__init__`. Found the hard way — `tests/live/wipe_db.py` is explicitly designed to be safe to run against an already-running server, but schema-once-at-construction meant deleting the underlying file out from under a live process left every later query hitting "no such table" until that process restarted. Cheap, idempotent, and closes exactly that gap.

**`DELETE /documents`** wipes every chunk in both stores (unioning both stores' `list_chunk_ids()` rather than trusting either alone, so it also repairs any pre-existing drift) and every row in `documents` — deliberately leaves query/feedback history alone, since that's a log of past activity, not corpus state, and stays meaningful after the corpus itself is reset.

**`DELETE /documents/{doc_id}`** is the single-document version of the same idea, scoped rather than wholesale: `HybridIndexer.delete_document(doc_id)` filters both stores' `list_chunk_ids()` by `startswith(doc_id)` before unioning and deleting — safe because `chunk_id` is `f"{doc_id}::{strategy}::{index}::{hash}"` (§5) and `doc_id` itself is a fixed-length sha256 hex digest, so one document's id can never be a prefix of another's. 404s if the `doc_id` isn't in `documents` at all, rather than silently reporting zero chunks deleted for a typo'd id.

**Conversations moved server-side**: `/query` originally took a client-supplied `history` list (capped at `max_length=10`), re-sent in full on every call. Replaced with a `conversation_id`: omitted, the server creates one; passed, the server loads that conversation's history from sqlite (windowed to the last 10 turns — the same bound, just enforced server-side now instead of at the request-schema layer) and feeds it to the agent. New `conversations` and `citations` tables (the latter one row per citation — marker, chunk_id, source, `pages`/`slides` as JSON-encoded lists, and (added later) `text`/`elements` — a full snapshot of that chunk's own content at citation time, `elements` also JSON-encoded, since sqlite has no native array/object column); `queries` gained `conversation_id` and `needs_clarification` columns. Both are declared in the `CREATE TABLE` DDL for a fresh database *and* self-healed onto an already-existing `queries` table via a small `PRAGMA table_info` + conditional `ALTER TABLE` helper — consistent with this file's existing self-healing-schema property (above), rather than requiring a manual reset for what would otherwise be a breaking schema change.

`GET /conversations/{conversation_id}` reconstructs a full turn history (question, answer, citations, refused, needs_clarification) for reload/resume — deliberately *not* paired with a `POST /conversations` (creation stays implicit in `/query`, matching how most chat APIs create a thread on the first message) or a list-all endpoint (no UI surface needed one yet).

### Identity and access control

`Principal` (`identity.py` — top-level, neutral, for the same reason `metadata.py` is: both `api/identity.py`, which builds one from a request, and `retrieval/scoped.py`, which uses one, need it, and `retrieval/` must never depend on `api/`, the same ports/adapters direction §1 already establishes) carries `principal_id`, `clearance`, and `is_admin`.

**`auth_mode="disabled"` (the default) is not a bypass branch — it's a real `Principal.unrestricted()`** (maximal clearance, `is_admin=True`) flowing through the *exact same* filter-construction code every other principal does. The alternative — an `if auth_mode == "disabled": skip filtering entirely` branch — would mean the scoping machinery is only ever exercised by a hypothetical "auth enabled" test suite, free to silently rot. Instead every test that goes through `POST /query` exercises `ScopedRetriever`'s wiring on every run; only the *content* of the filter it builds differs.

**`auth_mode="oidc"` validates a real bearer token** — signature (against JWKS, via `PyJWT`'s `PyJWKClient`, which does its own key caching), issuer, audience, expiry — not hand-rolled. The signing algorithm (`RS256`) is fixed by this code, never read from the token's own header: accepting an attacker-chosen algorithm is a well-known JWT verification bypass. An unrecognized `clearance` claim degrades to `"public"` rather than rejecting the token outright — an identity provider a step ahead of this deployment (a clearance level it doesn't know about yet) shouldn't lock out every one of its users.

**Two independent checks, one derived field.** `classification` (public/c1/c2/c3, cumulative — `metadata.clearance_or_below()` expands a caller's single clearance value into the whole range they're allowed) and sharing (`private`/`owner`, §12). The second is encoded as `acl_allow` — `["*"]` for a shared document, `[owner]` for a private one, `[]` for an unowned private one (visible to nobody: fail closed, not "shared by accident") — computed fresh every time `DocumentMetadata.to_payload()` runs rather than stored as its own field, so it can't disagree with `private`/`owner` *inside the model*. That guarantee stops at the model boundary: the denormalized copy in Qdrant/Elasticsearch is only as consistent as the writers that update it, and nothing but discipline and tests forces every writer to send the whole `to_payload()`. **Building this surfaced exactly that bug in last phase's `PATCH /documents/{doc_id}`**: sending only the changed fields to the store (correct for every other field, since Qdrant's `set_payload` merges) left `acl_allow` stale whenever a patch touched `owner` without also touching `private` — fixed by recomputing the *whole* metadata's payload from the merged row on every patch, not by special-casing which fields happened to change.

**`ScopedRetriever` (`retrieval/scoped.py`) sits below the agent, not inside it.** `AgentChain` lets the model choose its own tool arguments (§11) — a prompt-injected document could otherwise steer *what* gets searched, so the security filter has to live somewhere the model cannot reach or influence at all. It satisfies the same shape `RetrieverLike` (§11) already describes, so `AgentChain`/`RagChain` take one with no code change on their side; they never need to know scoping exists.

**Composing a mandatory filter with a caller-supplied one needed `SearchFilter` to grow a `merge()`** — deliberately not built in §10 ahead of a real second use. `merge()` **intersects** a field present in both filters rather than unioning it: a caller's `doc_ids`, or the agent's own tool arguments in a later phase, can only ever *narrow* what the security filter already allows, never widen or replace it. Asking for a classification the security filter doesn't already permit intersects down to `[]` (a real, indexed "matches nothing" clause — §10's `SearchFilter.any_of` — not a special case), not to a leak.

**A second, cheap check runs after the store search returns.** `ScopedRetriever` re-verifies every result against sqlite (`Database.get_documents_by_ids`) — the catalogue, not the (possibly stale) denormalized payload copy the store-level filter just used. This is what makes a permission change take effect immediately even before a repatch reaches the store, and what would surface a missing/unindexed payload field as a loud `ERROR` log line instead of a silent leak: the store-level filter is the one that has to scale, sqlite's is the one that has to be *right*, and checking only `≤ top_k` already-narrowed results keeps the second check cheap enough to always run.

#### The rest of the API

Search was the hard part because it needed store-level filtering; everything else is an ownership question, but leaving it open would have made the search work pointless — anyone could still list, read, or delete anything.

**Identity is attached where routers are included** (`main.py`), not on individual routes, so a router or route added later can't forget it. `/health` is the one exemption: a liveness probe has no user and touches no application data. A test walks the route table and fails if any endpoint is missing the dependency or isn't registered in the test file, so an unprotected endpoint fails on its own rather than depending on someone remembering.

**One rule, written once.** `Principal.can_see` and `Principal.can_modify` (`identity.py`) are the only statements of "who may see" and "who may change" a document. The document list, every lookup, the search post-check, and metrics all defer to them; search additionally expresses the same rule as a store filter because it must scale, but nothing else re-implements it. Editing or deleting is deliberately stricter than seeing: a shared document is visible to others but only its owner (or an admin) can change it.

**"Not found," never "forbidden," for what you can't see.** A 403 confirms that something exists, which is exactly what someone probing for other people's data wants to learn. So a document, conversation, or query the caller can't see returns the same 404 — same status, same response shape — as one that doesn't exist. A 403 appears only where the caller *can* see the thing (a shared document they don't own) or where the endpoint's existence isn't the secret (the admin-only wipe).

**Ownership comes from the caller, not the request.** At upload, a non-admin's `owner` is set to their authenticated identity regardless of what the request says — otherwise anyone could create documents "owned" by someone else. Admins (which is also what `auth_mode="disabled"` produces, whose `principal_id` is not a real person) keep the owner they name. Reassigning an existing document's owner is admin-only.

**The database is the enforcement point, the routers only shape the response.** Every `Database` method touching user data takes the `Principal` as a required first argument, and unscoped variants were removed rather than left around to be called by accident — a call that forgets the caller fails type-checking. Two deliberate exceptions to "scoped by visibility": a private `_fetch_document`, used only right after a write to return its result, and `get_own_document`, which answers "is this my document?" by *ownership* rather than visibility. The distinction matters because an owner can raise their own document's classification above their own clearance and stop being able to see it; ingest asks the ownership question, and asking the visibility one instead made a re-upload look like a brand-new document, skipped the chunk diff, and left the previous version's chunks behind in the stores (34 chunks became 39, still searchable). The regression test for that first passed vacuously — its control upload was swallowed as a duplicate of the very document it was meant to be compared against — and only failed once the control was ingested first and privately. Routers still check permissions *before* touching the vector/keyword stores (a refused delete must not have already removed the chunks); the database re-enforces afterwards as defense in depth.

**Closed leaks.** The duplicate-content check used to match against everyone's documents, so uploading a file you already had revealed — through `duplicate_of` — that someone else held it too; it now matches only documents the caller can see. `conversation_exists` used to gate `/query` without checking ownership, which allowed appending turns to another user's conversation. Metrics now describe only the caller's own conversations and visible documents (an admin sees the whole system), since global counts are identifying on a small deployment. Wiping the whole corpus is admin-only. Conversations gained an `owner` column; a row without one (from before the column existed) matches nobody but an admin, not everybody.

Building the scoped `metrics()` query is also where the new database tests earned their keep: the non-admin SQL had two `ON` clauses in one join, invisible to every test that used an admin.

## 14. Frontend

Streamlit, talking to the API **only over HTTP** — never importing `multimodal_rag` directly, which keeps the API a real architectural boundary rather than just an internal layering convention on paper.

Folder ingestion uses `st.file_uploader(accept_multiple_files="directory")` — a genuine native-OS folder picker (not a hand-rolled in-app directory browser, which was tried first and turned out unreliable for selecting subfolders in real browser use). Junk filtering (Office `~$` lock files, dotfiles, OS metadata) happens client-side before anything reaches `/ingest`, since the native folder picker has no per-file filtering of its own once a folder is chosen — and it has to live *outside* the surrounding form, since a form only exposes selected files to the script after submission, which would make it impossible to preview what's about to be skipped before committing to the click.

**Metrics staleness, and why it happened**: the Metrics/Documents panels sit earlier in the script's top-to-bottom render order than the chat input and feedback buttons. Streamlit reruns the whole script on every interaction — but *within one run*, code executes in the order it's written, so the metrics fetch (reading current state) happened *before* that same run's query or feedback mutation. Fixed with `st.rerun()` right after those specific mutations; `st.toast()` (not `st.success()`) for the resulting confirmation, since toasts are specifically designed to survive an immediate rerun where a normal message would be cut off mid-render.

**From a form to a chat**: the single question/answer form was replaced with `st.chat_message`/`st.chat_input`, rendering the full conversation as a scrolling transcript (`st.session_state.turns`, one entry per turn, shaped almost identically to the API's own `QueryResponse`/`ConversationMessageOut` so rendering code doesn't care whether a turn came from a live response or a reloaded `GET /conversations` call). `st.chat_input` has no per-message settings the way the old form did, so retrieval method/top_k moved into a persistent sidebar "Retrieval settings" expander instead — a necessary consequence of the primitive, not a preference. Every assistant turn gets its own 👍/👎 (keyed by that turn's `query_id`), not just the most recent one; the always-visible optional-comment text box was dropped in the same move, in favor of a compact per-message control closer to how real chat apps handle this.

**Resumable via URL, with an explicit fallback boundary**: `conversation_id` lives in `st.query_params`, not just session state, so a refreshed tab reloads the transcript from the server instead of losing it. An unknown/stale id in the URL (a bookmark after a DB wipe) degrades to a fresh conversation rather than erroring — the same `try/except httpx.HTTPError` discipline the `/health` check already used, reused rather than reinvented. One asymmetry accepted deliberately: `retrieved_chunks` (the full retrieved-but-uncited candidate set) isn't part of what the server persists, so a reloaded turn has no "Retrieved chunks" expander, while a turn generated live later in the same session does. Citations are the exception, not victim to this gap: each one carries its own `text`/`elements` snapshot taken at citation time (see §13), so a reloaded turn's citation buttons open the same real chunk-detail modal a live turn's do — this was the original design's actual complaint ("why can't I view details of chunks of previous conversations") and is why citations, specifically, don't need `retrieved_chunks` to work.

**Tag suggestions are LLM-proposed, never LLM-decided.** `POST /suggest-tags` (`routers/ingest.py`) previews candidate tags for a file before the user commits to ingesting it: parse the file (same `parse_document()` real ingestion uses, `summarize_tables=False` so this doesn't double the real LLM cost with table summaries), take an excerpt of its first ~20 elements' text (`ingestion/tag_suggestion.py`), and ask the LLM for up to 5 short tags as a JSON array, parsed defensively (same "extract the bracketed substring, catch a `JSONDecodeError`" discipline `judge.py` already uses for its own LLM-as-judge output). Writes nothing anywhere — no chunking, no embedding, no store or database row — so a failed or malformed response just means an empty suggestion list, the same fail-soft contract as `tables.py`'s `summarize_table()`. The frontend moved the single-file uploader **outside** the ingest form (same reasoning as the bulk uploader's own placement) so it can fire this call the moment a file is chosen and pre-fill the Tags field before the form is ever submitted — but the field stays a plain, editable text input: a suggestion is never written until the human looks at it and clicks Ingest, the same trust boundary already drawn around every other LLM-derived field in this project, applied here to one that also drives access-adjacent filtering.

**Caught while writing this feature's own tests: this project has no global fixture blocking a real LLM provider, unlike Langfuse** (§17's session-wide `tests/conftest.py` fixture blanks `LANGFUSE_*`, but nothing blanks the LLM provider settings). A test that never explicitly monkeypatches `get_llm` calls whatever's actually configured in a developer's own `.env.local` — an early version of this endpoint's "no LLM configured" test relied on ambient environment state instead of mocking it, and made a real, slow network call on a machine that happened to have a real provider configured. A second early test tried to prove the "unparseable file" fail-soft path with a `.md`-suffixed garbage-bytes file — markdown parsing is permissive enough to "succeed" on almost any byte content, so that file parsed fine and *also* made a real, unmocked LLM call. Fixed by monkeypatching `get_llm` explicitly in every test that could reach it, and by using a `.xlsx`-suffixed non-zip file to exercise a *genuine* parse failure (openpyxl reliably rejects non-zip content) instead.

**Tags are visible on click, not always shown.** The document list's per-document row became an `st.expander` (summary line: filename, version, chunk counts) rather than a flat row with everything printed at once — classification, owner, author, dates, and tags all crowd out the list at a glance if shown unconditionally, so they're one click away instead. The same expander carries a "Tags" text input pre-filled with the document's current tags and a "Save tags" button (`PATCH /documents/{doc_id}`, the existing metadata-only patch endpoint — no re-embedding), so a tag can be corrected or added long after ingest, not only at upload time. Both ingest forms (single-file and the bulk/folder path) gained matching "Author"/"Tags" text inputs — the bulk form's apply identically to every file in that batch, same as its existing classification dropdown already did, with a caption steering someone who needs per-file tags to the single-file form instead. An "Author" field had to be added at ingest at all, not just editable after the fact — without it, the Filters panel's author dimension would have nothing real in the corpus to ever filter by.

**The "Filters" panel (`st.dialog`) offers only values the corpus actually has.** Tags and author are `st.multiselect`s populated from the distinct values across the already-fetched `GET /documents` response (computed once, reused by both the corpus list and this panel, rather than fetching it twice) — never a free-text field, which is what keeps a filter selection from ever naming a value that matches nothing (the same principle the original plan named for the agent-tool version of this idea, applied here to the human-facing one instead). The date range is an `st.date_input` in range mode, bounded by the corpus's real earliest/latest `doc_date` — read as a single 2-tuple; a range widget returns a 1-tuple mid-selection (only the start date picked so far), which is guarded against explicitly rather than treated as a complete range. Selections are held in `st.session_state` (`filter_tags`/`filter_authors`/`filter_date_from`/`filter_date_to`) so they survive the dialog closing, applied to the next question via `QueryRequest.metadata_filter`; a `default=` list is filtered against the panel's current `options` before being handed to `st.multiselect`, since a previously-selected tag/author can vanish from the corpus (its last document deleted) and Streamlit raises if `default` contains a value `options` no longer has.

## 15. Testing philosophy

**Real services over mocks, at the store layer.** `QdrantStore`/`ElasticsearchStore` tests run against actual local Qdrant/Elasticsearch instances (via `docker-compose.yml`), not mocked clients — a store class is mostly a thin wrapper around real network calls, and mocking the client would mostly test the mock's fidelity to the real API, not the store's actual behavior. Provider-layer and chain-layer tests use fake/duck-typed implementations instead (`FakeEmbedder`, `FakeLLM`) — deterministic, free, fast, and appropriate once the layer under test doesn't depend on a *specific* backend's real behavior, just on the interface contract.

**A test has to be able to fail, and layered defenses hide that.** The lineage work checked its own tests by deliberately breaking the code and confirming the right test noticed — and one break went undetected: removing the access filter from the store query when history is requested still passed every test, because the catalogue post-check independently removes what shouldn't be seen, so the *result* stayed correct. The defense in depth was working; it also meant a result-level test couldn't see the layer beneath it. What the post-check cannot undo is the loss of recall — other people's documents crowd out your results before it runs — so the missing test asserts that: with `top_k=1` and someone else's private document as the closest match, the caller must still get their own. Two earlier cases of the same shape: a route-walking test that passed while inspecting zero routes (a framework upgrade had changed how routes are stored), and a regression test whose "control" upload was swallowed as a duplicate of the very document it was compared with. The recency work (§10) added two more of the same shape. Existing MMR and reranker tests caught a resort-by-`.score` step silently overwriting their own selection order — not by design, just because the running suite was checked after every change, not only the tests written for the new behavior. And two of the *previous phase's* own lineage tests caught family collapse silently defeating `include_superseded`: they had been written to expect both versions of a family back, before collapse existed to remove one of them, and a full-suite run — not the new phase's own tests, which never exercised that flag — was what caught the conflict. The habit: assert the thing being inspected is non-empty, break the code on purpose to watch the test fail, and run the *whole* suite, not only the tests that were just added — a later phase can invalidate an earlier phase's assumption without touching a single line the earlier phase's own tests would think to re-check.

**`retry_with_backoff` tests mock `time.sleep`**, not the retried operation — the point under test is the retry *logic* (does it retry the right number of times, does it eventually raise), and real sleeps would make the suite slow for no benefit.

**Live scripts, separate from the automated suite** (`tests/live/`): `start_all.py`, `wipe_db.py`, `stop_stores.py` — manual convenience tooling for actually clicking around the running app, explicitly *not* named `test_*.py` so pytest never collects them as tests. `start_all.py`'s shutdown handling specifically survives a second, impatient Ctrl+C during cleanup (escalates to a hard kill instead of crashing with a raw traceback) — caught via an actual live double-interrupt test while building it, not assumed correct.

**A session-wide `tests/conftest.py` autouse fixture blanks `LANGFUSE_*` env vars for every test.** Once retrieval tracing (§17) lives inside `Retriever.retrieve()` itself, *any* test that constructs a real `Retriever` -- not just tests that explicitly opt into exercising tracing -- reads real `Settings`, including whatever real Langfuse credentials happen to be sitting in a developer's own `.env.local`. Caught live, not by inspection: an ordinary `pytest tests/` run sent ~15 real `"retrieve"` traces to a real Langfuse Cloud project once `.env.local` had working credentials in it. Same class of bug as "silent real LLM call in tests," caught and fixed earlier for LLM/embedder providers -- a test must never depend on, or leak data to, a real external service just because local developer config happens to make one reachable. The fixture sets the string fields to `""` (not deletes them) specifically because pydantic-settings' precedence is OS env var over `.env` file -- deleting the OS var would just let the file's real value show back through; `LANGFUSE_ALLOW_CLOUD_HOST` (a `bool` field, no blank-means-unset normalization) needs an explicit `"false"` for the same reason. Tests that specifically exercise `get_langfuse_client()`'s own configuration logic (`tests/test_tracing.py`) monkeypatch `get_settings` directly, per test, and are unaffected by this fixture either way.

## 16. Known limitations, named on purpose

Each of these was a real judgment call, not an oversight — named here so they read as decisions, not gaps discovered later:

- **No cross-database transactions** between Qdrant and Elasticsearch (§9) — a single source-of-truth store both stores sync from independently would remove this, at real architectural cost.
- **No content deduplication across different documents** that happen to share text (§5, §12) — the fully general fix is a git-blob-style content-addressed storage layer decoupled from document membership; not built, named explicitly as the "textbook correct, more capable" answer.
- **No collection-name-scoped sqlite state** — `documents`/`queries`/`feedback` are one global table each, not partitioned per Qdrant collection. Only matters once more than one corpus is meant to coexist behind one API process, which hasn't come up yet.
- **Elasticsearch's standard analyzer splits on hyphens** (§8) — blurs exact-phrase precision for hyphenated identifiers; the real fix (a second `keyword`-typed field) is named, not built.
- **No schema migration framework** for the sqlite state — every column added since (`queries.conversation_id`/`needs_clarification`, `citations.text`/`elements`/`doc_id`, `documents.classification`/`private`/`owner`/`author`/`doc_date`/`data_type`/`tags`, §13/§12) goes through the same self-healing `PRAGMA table_info` + `ALTER TABLE` helper because each one, individually, was cheap enough to do properly — nullable or DEFAULT-bearing, additive only. That pattern has held for every schema change so far, not just the first one, but it's still not a migration framework: a column *rename*, a type change, or a constraint that can't be expressed as a DEFAULT would still need a full `wipe_db.py` reset, not an in-place migration. Proportionate for the current deployment scope; a larger multi-tenant deployment would need a formal migration framework.
- **`classification`'s sqlite DEFAULT `''` is a schema necessity, not a real value** (§12) — `ALTER TABLE ADD COLUMN` requires *some* constant default, but the application never writes `''` deliberately. A row that has it predates this migration; reading it directly raises, and lists, counts and lookups skip it with an `ERROR` log rather than letting one old row fail every endpoint. It is never given a classification, so it stays hidden and unsearchable until re-ingested. There is no backfill tool: the rows that exist are test documents, for which wipe-and-re-ingest is simpler than deciding on their behalf what classification they should have.
- **`owner` is caller-supplied for admins, and owners can freely change their own document's classification** (§12, §13) — for a non-admin, ownership comes from the authenticated identity, but an admin (and `auth_mode="disabled"`) names any owner it likes, and an owner may lower their own document's classification or upload above their own clearance (after which they can't see it themselves — it fails closed). Fine while owners are trusted; a real deployment would want a policy for declassification.
- **`data_type` is free text, not a closed vocabulary** (§12) — fine for storing and displaying, not yet reliable as a *filter*: two uploaders spelling the same document type two different ways ("Policy" vs. "policy") would silently split what should be one facet, and unlike `tags`/`author` (§10, §14) it has no UI surface yet that only offers values the corpus already has. `tags` and `author` are also still free text at ingest, but the drift risk is contained on the read side: the Filters panel only ever offers values actually present in the corpus (never free-typed), so a selection can't name a value that matches nothing — it just means two spellings of the same tag still show up as two separate filter options, not one.
- **Local, containerized dev has no MPS acceleration** — Docker on macOS runs inside a Linux VM with no GPU passthrough to Apple Silicon, so a containerized local stack falls back to CPU even though running the app natively on the same Mac gets MPS.
- **Grounding remains partly behavioral even where refusal sequencing is enforced** (§11) — search-before-refusal is now a code-level state-machine invariant, but a model can still misjudge nonempty evidence, substitute an adjacent fact instead of refusing, or cite using its own trained-in format. The citation-format case has a narrow code-level normalization for the variant observed live; factual entailment still needs evaluation rather than being fully enforceable by orchestration code.
- **`retrieved_chunks` isn't persisted, only citations are** (§13) — a reloaded conversation can show what was cited (citations carry their own `text`/`elements` snapshot, taken at citation time, so their detail modal works after a reload) but not the full retrieved-but-uncited candidate set from the original turn, which stays live-turn-only. A deliberate scope decision, not an oversight; revisit if that broader history ever matters for evaluation.
- **The Streamlit UI has no login path** (§13, §14) — with `AUTH_MODE=disabled` everything works exactly as before, but switching to `oidc` requires a bearer token on every request and the UI has no way to obtain or send one, so it stops working. Closing that means a login flow plus a shared HTTP client attaching the token at the twelve call sites that currently make bare requests; not built.
- **Replacing is owner-only, and two current versions of one family are not prevented** (§12) — a team can't publish version 2 of another team's document, and nothing stops two documents in a family both being `current` (uploading with no replacement, or undoing a replacement). §10's family collapse resolves this at *query* time (only the higher version reaches the model), not by preventing the state.
- **Retired documents are kept forever** (§12) — no retention or purge policy; history is a feature until it is a storage bill.
- **The recency tilt does not apply once results are reranked** (§10) — sound for the reason named there (a cross-encoder reranker never sees `.score`, so re-sorting its output afterward would overwrite its judgment, not nudge it), but it means the highest-precision retrieval path is the one recency can't influence. No "authority" ranking either (a policy outranking a meeting note) — that needs a tag that doesn't exist yet in the taxonomy, named, not added speculatively.
- **Old conversation citations keep a snapshot of the cited chunk's text** (§13) — a citation records the chunk's content at the time it was made, so if the source document is later made private or deleted, the conversation of whoever legitimately saw it still shows that text. Deliberate (it's what lets a reloaded conversation stay readable), but it means changing a document's access doesn't retroactively change what earlier answers already displayed.

## 17. Evaluation and observability

**Two independent metric layers, deliberately kept separate.** Retrieval metrics (`evaluation/retrieval_metrics.py`: `recall_at_k`, `mrr`, `ndcg_at_k`) are pure arithmetic over a ranked `SearchResult` list against a golden item's `expected_sources` — no LLM calls, no cost, deterministic. Generation metrics (`evaluation/judge.py`: faithfulness, relevance) are hand-rolled LLM-as-judge scores, not RAGAS — RAGAS pulls in its own `langchain`/`datasets` dependency tree that needs reconciling with the existing `litellm==1.85.0` pin, and doesn't know about this project's `LLMProvider` ports/adapters abstraction. `score_faithfulness(answer, context)` deliberately does NOT take the question (a question-aware judge risks rewarding "sounds like a good answer" instead of "is actually supported" — see the P95-for-P99 reasoning below); `score_relevance(question, answer)` deliberately does NOT take the context, for the same reason in reverse. An answer can be fully relevant and fully unfaithful at once (addresses the question, but isn't actually grounded in what was retrieved) — that's exactly the case independent scoring is built to catch, and a single fuzzy "is this good" score would hide.

**The golden set (`data/golden_set.json`) needs topical competition to mean anything.** Built against 5 documents that deliberately share vocabulary ("latency", "embedding", "index") without sharing content — a golden set with too few, too-distinct documents saturates recall@k at ~1.0 for every method regardless of ranking quality, since there's nothing for a bad retriever to actually get wrong. `_TOP_K` in `run_eval.py` is deliberately smaller than the corpus size for the same reason: recall@k can only fail when fewer documents fit in top-k than exist in the corpus. Caught live, not reasoned out in advance — an early 2-document version of the golden set, and later a `_TOP_K=5` run against a 5-document corpus, both saturated for exactly this reason before being fixed.

**Refusal-accuracy is scored separately from faithfulness/relevance, not through them.** A golden item with `expect_refusal: true` (e.g. "what was the P99 latency" when only P95 exists) makes no factual claims and isn't trying to answer the question, so faithfulness/relevance judges built for substantive answers would misjudge it — worse, a question-aware faithfulness judge shown "P95 exists, P99 doesn't" could reason a refusal is unnecessary given the closely-related data available, and reward exactly the P95-for-P99 substitution failure the agent's own system prompt (§11) already explicitly forbids. `refusal_accuracy` is a plain correctness check instead (did the chain refuse, yes/no) — the real test of hallucination resistance on the hardest case, without misapplying a judge built for a different job.

**`/metrics`'s `avg_latency_ms`/`feedback_rate` stay deliberately shallow** — no p95, no cost-per-query. That split is intentional: this endpoint is the cheap, always-on local summary (timed around the *whole* `agent.answer()` call, not one LLM completion, since a compound question can trigger multiple search/generate rounds and "latency of this query" means the full round-trip a caller actually waited through); percentile breakdowns and cost belong to Langfuse tracing, which computes them natively per-trace.

**Langfuse tracing is wired manually, not via litellm's `success_callback=["langfuse"]`.** This was a real, non-obvious blocker, not a style preference: `litellm==1.85.0` (pinned deliberately — see the LLM section) only declares compatibility with the OLD v2 langfuse client (`langfuse==2.59.7`), which itself pins `wrapt<2.0` — directly incompatible with `unstructured[pdf]`'s `wrapt>=2.1.1`, already a hard ingestion dependency. Confirmed by direct inspection, not assumption: litellm's `LangfuseLogger` does `langfuse.version.__version__`, a module that doesn't exist at all in the modern (v4, OpenTelemetry-based) client this project actually installs. `tracing.py` instruments `litellm.completion()` calls manually instead, via `Langfuse.start_as_current_observation(as_type="generation"|...)`. Nesting (every search + every LLM call of one `/query` turn under one trace, every turn of one conversation grouped under one session) comes for free from OpenTelemetry's own context propagation — no manual `trace_id` threading through `LLMProvider`'s interface was needed, which matters because that interface is implemented by fake test doubles in a dozen+ test files; adding a required parameter there would have broken all of them for a purely optional feature.

**Retrieval is instrumented at the source (`Retriever`), not reactively from `AgentChain`'s callback.** The original approach logged one `create_event()` (a point-in-time marker, no duration) from `AgentChain.answer()`'s existing `on_tool_call(round_index, query, results)` hook -- but that hook fires *after* a search already completed, with no start time to measure against, and it only covered what one specific caller (`AgentChain`) chose to report. Superseded by wrapping the actual embedder/Qdrant/Elasticsearch/reranker calls directly inside `Retriever.retrieve()` (`retrieval/retriever.py`) with `tracing.traced_span()` -- a generic sibling of `traced_generation` using Langfuse's own `"retriever"`/`"embedding"` observation types where they fit. This gives real per-step timing (`retrieve` as one parent span, `embed_query`/`qdrant_search`/`elasticsearch_search`/`rerank` as its timed children) and makes retrieval tracing automatic everywhere `Retriever.retrieve()` is called -- `RagChain`, `demo.py`, `run_eval.py` too, not just the interactive `/query` path via `AgentChain`. `on_tool_call` itself is untouched and still serves `demo.py`'s console printing; `routers/query.py` no longer needs to wire it into tracing at all. The span's `output` is a compact per-result summary (source, score, pages/slides, a ~300-character text preview) -- deliberately not the full `SearchResult` (whose `.elements` can carry base64 image data, and whose `.text` can be the full resolved-parent section, up to 8000 characters) -- so a trace stays legible in the UI rather than becoming a payload dump.

**The public Langfuse Cloud is refused by default, independent of `allow_external`, with a separate deliberate opt-in.** `allow_external` answers "may this profile call any external service at all" — true on an ordinary company laptop, since it needs to reach the company's own external LLM gateway. That is a different question from "may this specific data (real user questions, answers, retrieved document content) be handed to a third party's cloud," which has to default to no even when the first answer is yes; conflating the two would mean a laptop set up to reach an approved company AI endpoint could just as easily leak confidential query content to `cloud.langfuse.com` the moment someone pasted in API keys. So `get_langfuse_client()` blocks `cloud.langfuse.com` and its regional variants (`us.`/`eu.cloud.langfuse.com`) before the `allow_external` guard ever runs, and separately refuses to default a blank `LANGFUSE_HOST` to that same address the way the SDK itself would — tracing only activates once someone explicitly names a real (intended to be self-hosted) host. A second, independent setting, `langfuse_allow_cloud_host` (`LANGFUSE_ALLOW_CLOUD_HOST` in `.env`), lifts the cloud-specific block for the rare, genuinely-fine case — e.g. a personal dev machine with no confidential documents — but only that block: an air-gapped profile (`allow_external=False`) still refuses the cloud even with the opt-in set, since the general external-host guard runs independently afterward. The existing `allow_external`/internal-host guard (§ privacy guard) still applies on top, for any *other* external address on an air-gapped profile. Every blocked case disables tracing with a logged warning rather than raising — tracing must never be a reason a real query fails, but silently going dark would leave a developer unable to tell why traces never show up.

**Every direct Langfuse SDK call is wrapped defensively, not just the "not configured" case.** `get_langfuse_client()`, `traced_query`, `traced_span`, `traced_generation`, and `record_generation_result` all originally only handled tracing being *unconfigured* as a no-op — a Langfuse hiccup *after* successful configuration (host unreachable, service down, a network blip) could still have broken a real, already-succeeded query. Two failure classes needed separate fixes: (1) `get_langfuse_client()`'s own `Langfuse(...)` constructor wasn't guarded, and worse than crashing once — `@lru_cache` doesn't cache a raised exception, so every future request would retry (and re-fail) construction forever, once configured; fixed by catching the failure and returning `None`, which *is* what gets cached. (2) every span open/close and `.update()` call needed its own try/except, especially `record_generation_result()`'s, which runs right after a real, successful LLM response comes back — a tracing failure there must not be able to take that already-obtained answer down with it. `_safe_enter`/`_safe_exit` helpers centralize this for the open/close case; verified with tests that inject failures at each exact point and confirm the wrapped work still completes, plus one confirming a REAL exception from the wrapped business logic still propagates normally (tracing swallows only its own failures, never a real one).

**`traced_query`'s own "query" span silently had no `input`/`output` for a while — caught by the user noticing it in the Langfuse UI, not by review.** Every other observation (`generate_with_tools`, `embed_query`, `qdrant_search`, ...) was built with `input=...` at creation and had its `output` attached before closing; `traced_query`'s `start_as_current_observation()` call was only ever given `metadata={"query_id": ...}`, and the function yielded nothing, so `routers/query.py` had no handle back to the span to attach the final answer to even if it had wanted to. Fixed by having `traced_query` take the question as a parameter (set as `input` at creation) and yield the span itself, so the caller calls `update_span_output(span, result.answer)` once the real answer is known — the same pattern `traced_generation`/`traced_span` already followed; `traced_query` was just the one call site that never got it.

**Since retrieval tracing moved inside `Retriever` itself, any test constructing a real `Retriever` — not just tests deliberately exercising tracing — was silently reading real `Settings`, including real Langfuse credentials sitting in a developer's own `.env.local`.** Caught live, not by inspection: an ordinary `pytest tests/` run sent ~15 real `"retrieve"` traces to a real Langfuse Cloud project once `.env.local` had working credentials in it — the exact "silent real network call in tests" failure mode already caught once for LLM/embedder providers, recurring here for a different subsystem. Fixed with a session-wide `tests/conftest.py` autouse fixture that blanks `LANGFUSE_*` env vars for every test. The fixture sets the string fields to `""`, not deletes them — pydantic-settings' precedence is OS env var over `.env` file, so deleting the OS var would just let the file's real value show back through; `LANGFUSE_ALLOW_CLOUD_HOST` (a `bool` field, no blank-means-unset normalization) needs an explicit `"false"` for the same reason. Tests that specifically exercise `get_langfuse_client()`'s own configuration logic (`test_tracing.py`) monkeypatch `get_settings` directly, per test, and are unaffected either way.

**The golden set now also runs as native Langfuse Experiments** (`evaluation/langfuse_experiment.py`, `uv run python -m multimodal_rag.evaluation.langfuse_experiment`) — one dataset run per retrieval method, so "hybrid+rerank beat cosine on faithfulness" is a comparison Langfuse's own UI renders natively (per-run averages, run-vs-run diffing over time via a real clickable Dataset Run URL), not just a table `run_eval.py` prints once and forgets. This is additive, not a replacement — `run_eval.py`'s console-only comparison still exists and needs no Langfuse configuration at all, which matters on a profile (e.g. the air-gapped server) where Langfuse may never be set up.

`data/golden_set.json` is synced into a Langfuse Dataset on every run via `create_dataset`/`create_dataset_item` — both verified live to be genuine upserts keyed by name/id (calling either twice with the same name/id updates the existing one in place, no duplicates), so this is safe to call unconditionally rather than needing an existence check first, and a golden-set edit (a new question, a corrected `expected_sources` list) shows up on the next run automatically. Each golden item's own `id` is reused as the dataset item id specifically so this stays true.

The actual scoring logic isn't reimplemented for Langfuse — `run_experiment()`'s `evaluators` are thin adapters around the exact same `retrieval_metrics.py`/`judge.py` functions `run_eval.py` already uses and already has unit tests for. `recall_at_k`/`mrr`/`ndcg_at_k`'s signatures were widened from `list[SearchResult]` to a structural `HasSource` Protocol (they only ever read `.source`) so a lightweight `_SourceOnly` stand-in works too — deliberate, not incidental: the experiment task returns a JSON-serializable summary (`retrieved_sources: list[str]`, a plain answer string, refusal flag, assembled context text), never real `SearchResult` objects, so a trace's `output` never risks carrying `.elements`' possible base64 image data the way passing the real objects through would have. Faithfulness/relevance evaluators catch `JudgeParseError` themselves and return no evaluation for that item rather than letting a malformed judge response take down the whole experiment run — same "one bad item shouldn't sink the batch" precedent `run_eval.py`'s own judge-failure counting already established.

**The expert eval is one script that always prints to the console and opportunistically also sends to Langfuse — it used to be two, and running the wrong one was a real, live-hit point of confusion.** `run_expert_eval.py` (console-only) and `langfuse_expert_eval.py` (Langfuse Experiment) were separate commands; someone ran the console one expecting a new Experiment and saw none, and saw `generate_with_tools` traces still disconnected — both symptoms of the same fact (the console script never touched Langfuse's Dataset/Experiment API, and has no trace-grouping context of its own; only Langfuse's `run_experiment()` opens one per item). Fused into `run_expert_eval.py`, deleting the other. The design that makes it one script instead of two scripts glued together: scoring and aggregation are shared, and only the *driver of the loop* differs. The evaluators (`_correctness_evaluator`, `_refusal_accuracy_evaluator`) emit `Evaluation` objects either way; `_aggregate()` derives every number in the console table (average correctness, refusal accuracy, false refusals, judge parse failures) purely from those evaluations; `_run_locally()` drives the loop when Langfuse isn't available, `_run_on_langfuse()` hands it to `run_experiment()` when it is and maps its `item_results` back into the same shape. So the console table means the same thing in both modes, by construction rather than by keeping two copies in sync — a judge parse failure, for instance, is derived as "an answerable item that produced neither a correctness score nor a false-refusal flag", which holds identically whichever runner produced it.

**"Can it connect" is decided by `auth_check()`, not by `get_langfuse_client()` returning something.** The latter only proves the settings looked usable (keys present, host allowed by the privacy guard) — constructing the client makes no network call — so a wrong key or an unreachable host would otherwise only surface as an exception deep into a multi-minute run. `_connect_langfuse()` returns the client or `None` plus a message saying which case applies (not configured/blocked, auth check raised, auth check returned false, or connected); the message is printed up front and again under the table, since a run's LLM-call log noise scrolls the first one away. It never raises: a missing or broken Langfuse must never be the reason an eval can't produce its result.

**One latent divergence between the two modes had to be closed for "same result either way" to be true: stale dataset items.** `create_dataset_item` upserts by id but never deletes, so a question removed or renamed in `qa.json` stays in the Langfuse dataset forever — and `run_experiment()` runs whatever the dataset holds, so the connected mode would silently keep asking and counting it while the console-only mode wouldn't. `_run_on_langfuse()` filters `dataset.items` to the ids `qa.json` has right now (`run_experiment()` reads that public attribute at call time — checked in the SDK rather than assumed), so both modes always evaluate exactly the same questions.

**The expert eval could not exercise Phase 5/6 at all until documents carried real metadata.** `build_expertise_agent()` ingested every expertise's documents with no `DocumentMetadata` at all — no classification, no `doc_family_id`/`version`/`status`/`effective_from`. Fine for plain retrieval quality, but family collapse and the recency tilt (§10) both key off fields that path never set, so no expert-eval question could ever depend on either actually working. An optional `documents_metadata.json` sidecar (filename → `DocumentMetadata` fields) fixes this without touching the "just add files" convention (§ above): a filename with no entry keeps the old default (a bare `classification: "public"`), and indexing moved from one shared `HybridIndexer.index()` call over every document's chunks at once to one call *per document*, each with its own metadata — `doc_metadata` is a single value per call, so a shared call could never have expressed "these two documents disagree about their own lineage" in the first place. `company-spreadsheets` uses it for two real cases, deliberately different mechanisms: a **declared** supersession (same `doc_family_id`, versions 1 and 2, the old one `status: "superseded"`) proves the stale figure never reaches generation at all (family collapse removes it from the pool structurally); an **undeclared** conflict (two unrelated, independently dated documents, no family relationship) proves the opposite case — both chunks reach the model, and the correct answer depends on it applying `CONFLICT_RESOLUTION_RULE` to the dates shown in its own context, the exact scenario Phase 6 was built for.

## 18. Tabular data — embedding vs. generation diverge for tables

**A table's LLM summary was computed since early in this project but never actually used.** `ingestion/tables.py`'s `summarize_table()` has been called by every format parser with a native table (PDF, DOCX, PPTX, Markdown) from early on, storing the result on `Element.table_summary` — but `chunking/text.py`'s `element_text()` (what actually becomes `Chunk.text`, i.e. what gets embedded and searched) only ever read `element.text`, the raw markdown rendering. Found by tracing `table_summary` through the whole pipeline on request, not by design review: it was set at parse time and read nowhere else. In effect, every table was searched via its raw markdown — mostly punctuation and short repeated cell tokens, which embeds poorly for semantic matching — while images/charts, via the same `element_text()` function, *did* get their vision-LLM `description` embedded, exactly the multi-vector pattern tables were supposed to get too.

**Fixed by making `element_text()` prefer `table_summary` for `ElementType.TABLE`, falling back to the raw markdown only when no summary exists** (unconfigured LLM, or a failed `summarize_table()` call — it already fails soft, returning `None`). This is a one-line change, but its effect is conditional: it only does anything where a summary was actually generated, and **nothing in production generates one** (`summarize_tables` defaults to `False` and no caller sets it — see the open defects at the end of §4). As shipped, the code path is implemented and unit-tested but inert; an earlier version of this paragraph claimed it "fixes retrieval for every table across every existing parser", which overstated it.

**Embedding and generation had to be made to diverge, since they'd shared one field.** Once a table's embedded text is a short summary, the generator can't be shown that same summary — it needs the real numbers to answer a question about them, not a paraphrase. The fix reuses infrastructure that already existed for a different reason: `Chunk`/`SearchResult` already carry an `elements: list[ChunkElement]` snapshot of the original elements behind a chunk (built for letting the frontend display "an actual rendered table, an actual image" instead of only the flattened blob), and `ChunkElement.text` already holds the *raw* table markdown, never the summary — no new field was needed. `generation/context.py` gained `_generation_text(result)`, which reconstructs the real per-element text from `result.elements` (raw table markdown for tables, vision description for images/charts — unchanged from what's embedded, since only tables diverge) whenever any table element is present, and falls back to `result.text` for everything else — meaning it's a no-op for non-table chunks and only actually changes behavior where a table is involved. Both `format_context_block()` (what the generator reads) and `assemble_context()`'s token budgeting were switched to it — budgeting against the cheap embedded summary while the real (potentially much larger) table is what actually gets sent would have silently let the true token budget blow past what was ever counted.

**Known limitation — and larger than it was first judged to be.** This paragraph originally said the problem only arises if a caller generates directly from an un-resolved child chunk (`resolve_parent_context=False`), which no real call site does. That was wrong about its own scope. `ParentChildChunker` attaches the same `parent.metadata.elements` — the whole *section's* elements — not only to every child but to every *parent* of a section that gets split, and `_generation_text` rebuilds the generator's text from all of them whenever any is a table. So it bites on the normal path (`resolve_parent_context=True`) for any section that is both large and contains a table — which is every CSV/Excel file, since spreadsheets have no title elements and the whole file is therefore one section. Measured on a 600-row CSV: one hit on a parent that itself holds 7,514 characters (2,994 tokens) makes the generator's context 25,308 characters (about 9,980 tokens) — the entire file's tables — against a 2,000-token budget, and `assemble_context` deliberately keeps the top result even when it alone exceeds the budget. It grows linearly with file size and repeats for every parent of the same file. Not fixed yet. The candidate fixes trade off differently — rebuild only when a summary was really embedded (a no-op today, since none is), attach to each parent only the elements overlapping its own text, or give each sheet its own section — so it wants a decision, not a drive-by patch.

## 19. CSV/Excel ingestion — row-batching instead of one-Element-per-table

**Real spreadsheets break the existing table model.** `ingestion/tables.py` turns a whole table into one `Element` — fine for a hand-authored, small DOCX/PDF table, but a CSV or Excel sheet can be hundreds or thousands of rows. One giant `Element` would either blow past a reasonable `summarize_table()` LLM call, or get mid-row-sliced downstream by the character-based `ParentChildChunker` with no idea where a row boundary is — misaligned columns, no header, useless for retrieval.

**New shared module `ingestion/tabular.py`** batches rows into groups of `ROWS_PER_ELEMENT` (30, a starting point — not golden-set-tuned the way `child_chunk_size` was), rendering the header at the top of *every* batch via the same `rows_to_markdown()`/`summarize_table()` helpers `tables.py` already provides — reused, not reimplemented. Each batch becomes its own self-contained `TABLE` Element, independently self-describing regardless of which part of a large sheet it came from. That guarantee holds at the *Element* level, not at the level of what retrieval actually matches: the elements then go through `ParentChildChunker` like any others, whose ~200-character children are what get searched, so only the first child of each batch carries the header (§4, "What that means for a spreadsheet"). Rows do stay whole — the child splitter prefers line breaks, and no child in the measured example ends mid-row — but an earlier version of this paragraph described the batching as "the chunking", which it isn't. `csv_.py` (Python's stdlib `csv` module, no new dependency) and `excel.py` both build on this.

**Deliberately does not try to detect a "real" header row among leading title/note rows.** Real spreadsheets often have a few rows of free text above the actual column header — reliably telling those apart from the real header (merged cells, multiple header rows, notes below instead of above, more than one table per sheet) isn't a problem a heuristic can be trusted to get right. Every batch is rendered as-is, whatever rows are actually in it; the LLM summary (§18) is what's meant to describe what a batch actually contains even when the first row of a batch isn't really a header — a summary just reads the batch, it doesn't need to know which row is which. That only works once summaries are generated, which today they aren't (§4, open defects); until then a batch is embedded as its raw markdown.

**Excel support (`ingestion/excel.py`, `openpyxl`) is `.xlsx` only, deliberately.** Legacy `.xls` needs a different, largely unmaintained library (`xlrd`, which itself dropped `.xlsx` support when maintenance wound down), and `openpyxl` doesn't support it at all — not worth a second dependency for a format phased out over a decade ago. Each worksheet is treated as its own logical table (one call into the same `tabular.rows_to_elements` CSV uses, with `sheet=worksheet.title` — no attempt to detect more than one table per sheet, same "don't guess at structure" choice as the header row). Loaded via `data_only=True` so a formula cell reads Excel's own last-calculated value ("42"), not the formula string ("=SUM(A1:A10)") — the value is what's citable and matchable; the formula isn't.

**Embedded pictures are extracted through the same vision pipeline DOCX/PPTX already use** (`ImageDescriber`, one instance per workbook) — often where the real insight in a real spreadsheet actually lives, in a chart someone pasted in as an image, not just the raw numbers. This is why `openpyxl.load_workbook()` is called WITHOUT `read_only=True`: read-only mode is openpyxl's own documented tradeoff that drops access to embedded pictures entirely, and reusing one workbook load for both row data and pictures matters more than read-only's memory savings at this project's scale. Reading them at all requires `worksheet._images` / `image._data()` — openpyxl's own PRIVATE API, since there's no public accessor for embedded pictures in an existing file at all (confirmed by research, not assumed: openpyxl's image/chart classes are built for *writing* new files, not parsing existing ones). Flagged explicitly as a fragility risk that could silently break on an openpyxl upgrade, not hidden behind a normal-looking public call.

**A native Excel CHART (built live from cell data, not a pasted-in picture) is a genuinely different, harder problem — researched, not guessed at.** Confirmed via openpyxl's own documentation: it cannot read an existing chart's definition at all, only create new ones — reading `worksheet._charts` on a loaded file returns nothing. The commercial alternatives that *can* render a chart to an image (e.g. Spire.XLS) have real free-tier limits (a 3-page cap on Excel-to-image conversion) and cost money unlimited; LibreOffice headless conversion is free but has no confirmed way to export a single isolated chart rather than a whole rendered sheet, and would add a full office-suite runtime dependency. The approach actually taken instead (`excel_charts.py`) needs neither: a `.xlsx` is just a ZIP of OOXML XML parts, and a chart's own definition lives at `xl/charts/chartN.xml` in the standard, documented chart schema — readable directly via stdlib `zipfile` + `xml.etree.ElementTree`, no new dependency, no license, no extra runtime. This describes what the chart's DATA says (type, title, series, referenced ranges resolved against the sheet's own cell values, via the LLM the same way `summarize_table()` already describes a table) rather than what the chart visually looks like (colors, manual annotations aren't in the data model) — the right fidelity for "what insight does this communicate," not a substitute for "what does it look like."

**Charts aren't named per-sheet in a `.xlsx`, so attributing one to the worksheet it's actually on needs the real OOXML relationship chain, not a guess.** `xl/charts/chart1.xml` doesn't say which sheet it belongs to — the file only says a chart exists somewhere in the workbook. `charts_for_worksheet()` follows the real chain: `worksheet._rels` (openpyxl's own private but already-resolved link — it saved having to hand-parse `workbook.xml`'s sheet-name-to-part-name mapping) gives the worksheet's drawing part (e.g. `xl/drawings/drawing1.xml`); that drawing's own `_rels` file (read directly, since this part isn't exposed through openpyxl at all) lists the charts it actually embeds. Verified empirically against a real openpyxl-generated chart, not assumed correct from reading the OOXML spec alone — including resolving a series' cell-range reference (`'Sheet1'!$B$2:$B$4`) into real values via `openpyxl.utils.cell.range_boundaries()` plus the workbook already loaded for row data, rather than hand-rolling A1-notation parsing.

**Scoped to "category axis" chart types (bar/column/line/area/pie), with a named fallback for the rest.** These all share the same `<cat>`/`<val>`/`<tx>` series shape in the chart schema; scatter/bubble/stock/surface charts use different reference tags (`<xVal>`/`<yVal>`, ...) this parser doesn't attempt to resolve. Rather than silently dropping those charts or crashing on them, an unsupported type still produces a minimal type+title description — "a bar chart named X, data series could not be parsed" is more honest and more useful than nothing at all.

**`data/samples/sample.xlsx` was deliberately strengthened past a toy fixture, at the user's explicit request, specifically to surface silent failure modes a tiny synthetic file can't.** It now carries a real embedded picture, a genuinely long table (85 rows on the "Notes" sheet — several `ROWS_PER_ELEMENT` batches, not one) with a distinctive marker in its LAST row, and a native chart built from that same table. Run live against the real parser (not just asserted in a mocked unit test), this actually caught something worth catching: `describe_chart()`'s data resolution is correct enough that the LLM-written summary of the chart spontaneously called out the day-85 anomaly in the underlying numbers — real end-to-end proof the pipeline resolves real values, not just chart structure.

**That same fixture change caught a second, unrelated regression: `test_dispatcher.py`'s xlsx routing test started making a real LLM call inside what's supposed to be a fast, fully-mocked unit test.** The test only stubbed `get_vision()` (for the picture), not the chart-specific `_summarize()` call — once `sample.xlsx` gained a real chart, every run of that one test silently started hitting the real configured LLM provider. The exact same "silent real network call inside pytest" failure class already caught twice before this session (LLM/embedder providers directly, then Langfuse tracing via `Retriever`) — confirmed for real this time by monkeypatching `get_llm` with a call-counting spy rather than trusting wall-clock timing alone, then fixed the same way as before: an autouse fixture stubbing the specific call site, not a blanket "don't test this" workaround.

**Ingestion's LLM calls were only *half*-traced, and the missing half was found from a user noticing an asymmetry in the Langfuse UI, not from code review.** `summarize_table()`/`describe_chart()` (both go through `get_llm()` → `LiteLLMProvider.generate()`) were already individually traced — that wrapping lives in the *provider* layer (`providers/llm.py`'s `traced_generation`/`record_generation_result`), not in ingestion code at all, so it was easy to miss that it was already happening. `LiteLLMVisionProvider.describe()` (`providers/vision.py`) had no equivalent wrapping at all — a real, asymmetric gap, not a misunderstanding: a table summary's trace existed, a picture's never did. Fixed by adding the identical `traced_generation`/`record_generation_result` pair to `describe()`, with one deliberate difference from the text path: the traced `input` is a placeholder (`"[image: N bytes, image/png]"`), never the real base64 payload, for the same reason retrieval tracing already keeps `SearchResult.elements`' possible image data out of a span's output — a trace should stay legible, not become an image-byte dump.

**Every one of those generation traces was also an orphan — its own disconnected root trace, never grouped with the document it came from or with each other.** Fixed at the single choke point every caller of every parser already goes through, `ingestion/__init__.py`'s `parse_document()` — wrapped in one `traced_span("ingest", input=<path>)`, the same "instrument at the source, not reactively from one caller" choice `retrieval/retriever.py` made for retrieval tracing. Every LLM call a parser triggers while it runs nests under this automatically via OpenTelemetry's context propagation, with zero changes needed inside `tables.py`/`excel_charts.py` themselves — their tracing was already there, it just had nothing to nest under. Verified live and structurally via the Langfuse API (the same v2-observations endpoint used earlier in this project, since this org's single-trace/single-observation endpoints are deprecated — 410/404): one real ingestion of `sample.xlsx` with `summarize_tables=True` produced exactly one `ingest` span with 6 children (4 table-summary generations, 1 chart-summary generation, 1 picture-description generation), every one correctly parented to it — the API can't return `input`/`output` text content for this org, but the code setting them is the identical mechanism already visually confirmed working for query traces.

**Reading the verification API's *default* response cost real debugging time, until its `fields` parameter was found — a lesson worth stating on its own.** `client.api.observations.get_many()` silently omits `metadata`/`input`/`output` unless `fields` explicitly names them; the exact same observation returns `metadata: None` without `fields` and the real dict with it. This looked, briefly, like a genuine bug in the tracing code — it wasn't. Same underlying lesson as the deprecated single-trace/observation endpoints found earlier: this API's default response shape is not its full response shape, and treating a default response as ground truth risks reporting a false negative rather than an honest "inconclusive." Verification here on uses `fields=` explicitly whenever *content*, not just structure, needs confirming.

**Retrieval's real "thinking" — RRF fusion and MMR's diversity-vs-relevance selection — had no span at all, confirmed both by reading the code and by a live trace's actual observation order.** A trace showed `qdrant_search`/`elasticsearch_search` each returning `candidate_pool` (20) results, then nothing until `generate_with_tools` received the final `top_k` (5) — the computation that turned 20+20 candidates into 5 was real, pure Python, and completely untraced; a viewer could see the inputs and the outcome but never the decision in between. Fixed with two new child spans mirroring the existing `rerank` span's shape: `rrf_fuse` (metadata: `rrf_k`, candidate counts from each source; output: each surviving chunk's fused score and whether it was found by vector search, keyword search, or both — "found by both" being the specifically interesting RRF signal) and `mmr_select` (metadata: `mmr_lambda`, candidate count; output: each pick in selection order with its relevance and final MMR score, showing the actual diversity trade-off, not just the outcome). The outer `retrieve` span's own metadata gained `candidate_pool`/`rrf_k`/`mmr_lambda` (the latter two `None` when not the active method) — without them, a child span showing `top_k=20` had no visible link back to why 20 rather than the 5 actually requested. The retrieval **method** itself was already captured correctly in metadata (confirmed live, not assumed — `fields=` again), just not visible at a glance, since Langfuse's default trace-tree view doesn't expand metadata; moved into the span's own **name** too (`retrieve[hybrid_rrf]`, not just `retrieve`) so it's never hidden behind a panel that needs opening. All of it verified against a real trace after the fix, not just asserted in a mocked test: `retrieve[hybrid_rrf]` → `embed_query` → `qdrant_search` → `elasticsearch_search` → `rrf_fuse`, with `rrf_fuse`'s real metadata showing `vector_candidates: 20, keyword_candidates: 20, rrf_k: 60`.
