## 1. Overall shape: ports & adapters

Every swappable concern (LLM/embedding/vision/reranker providers, vector store, keyword store) is split into an **abstract interface** (`*/base.py`) and **concrete implementations**, constructed only by a single `factory.py` per module. Calling code depends on the interface, never on a concrete class (`QdrantStore`, `LiteLLMProvider`) directly.

**Why**: the entire premise of the project is that pieces get swapped — chunking strategy, embedding model, vector backend — while iterating. Ports & adapters makes "swap the vector store" a one-file change (the factory), not a grep-and-replace across the codebase. `Retriever` is the one deliberate exception: it's *not* an ABC, because retrieval *method* is chosen per-query by the caller (a UI dropdown), not per-deployment-environment the way providers/stores are — a different axis of variation, so it doesn't fit the same pattern.

**Cost**: an extra layer of indirection for every module, and the discipline of never letting a concrete class leak into calling code (even for something as small as "just check `isinstance(store, QdrantStore)`"). Worth it here because the swapping is real and expected, not hypothetical.

## 2. Environment portability

`RAG_ENV` (an OS environment variable, read *before* pydantic loads anything, since it decides *which* file to load) selects `.env.local` or `.env.server`. Both files populate the same `Settings` model (`pydantic-settings`), so the rest of the app never branches on environment — it just reads `Settings` fields that happen to differ.

**The privacy guard**: on the server profile (`ALLOW_EXTERNAL=false`), `enforce_privacy_guard()` checks every provider's `base_url` against loopback/private IP ranges before construction — an external URL raises immediately, not "might silently phone home." Also forces `HF_HUB_OFFLINE=1`/`TRANSFORMERS_OFFLINE=1` so the moment a `sentence-transformers` model isn't already cached, it fails loudly instead of hanging on a DNS lookup that never resolves on an air-gapped box.

**Trade-off**: this is a *structural* guarantee, not a network-level one — it stops the *application* from calling out, not a compromised dependency from doing so. A real air-gapped deployment still wants network-level isolation (firewall rules) as the actual boundary; the privacy guard is defense sitting inside that boundary, not a replacement for it.

## 3. Providers layer

`LiteLLM` is the mechanism that makes "same code, different backend" possible for LLM/embedding/vision calls — any OpenAI-compatible endpoint (real OpenAI, an internal company gateway, a local vLLM server) is reachable through the same `litellm.completion()`/`litellm.embedding()` call, differing only by `model`/`base_url`/`api_key`. LangChain's own model-wrapper classes were deliberately *not* used for this, even where LangChain is used elsewhere (the generation chain) — those wrappers would reintroduce vendor coupling at exactly the point the whole providers layer exists to avoid.

**Local embeddings** (`SentenceTransformerEmbeddingProvider`) run entirely offline once the model is cached — no network call at all, which is what makes them safe on the air-gapped profile. **Hosted embeddings** (`LiteLLMEmbeddingProvider`) manually batch input (LiteLLM doesn't batch for you, and real APIs cap request size) and retry each batch with exponential backoff; a persistently-failing batch doesn't abort the whole call — already-embedded batches are kept and returned alongside which texts failed, so a caller can decide to use the partial result or retry just the gap. Constructing the underlying `openai.OpenAI` client explicitly (rather than letting LiteLLM build its own internally) turned out to matter for one specific reason: on a corporate network requiring `truststore`'s SSL patch (see below), LiteLLM's own internally-constructed client didn't reliably pick that patch up.

**Corporate proxy support** (`TRUST_SYSTEM_CERTS`): a TLS-inspecting corporate proxy presents certificates signed by an internal CA that the OS trusts but Python's bundled `certifi` CA list doesn't. `truststore.inject_into_ssl()` patches the `ssl` module to defer to the OS trust store instead. Gated behind a settings flag, default off — inert everywhere the flag isn't set, so it never changes behavior on Linux, CI, or a Mac.

**Tool-calling as an optional capability**: `generate_with_tools()` was added to `LLMProvider` for the agent loop (§11) to get structured tool calls back, not just text — as a *concrete* method with a `NotImplementedError` body, not `@abstractmethod`. Making it abstract would have broken every existing subclass (`InternalServerLLM`, every test's `FakeLLM`) that only ever implemented plain `generate()`; an optional capability layered onto a required interface shouldn't force every existing implementer to react the moment the capability is added. `LiteLLMProvider` implements it via `litellm.completion(..., tools=...)`; `InternalServerLLM` inherits the same not-implemented stub its plain `generate()` already has.

## 4. Ingestion

File type is detected from actual file **content** via `libmagic`, not the extension — a renamed or extensionless PDF still routes to the PDF parser. Markdown is the one exception: plain text has no distinguishing magic bytes, so `libmagic` can only ever report `text/plain`, and the dispatcher falls back to the file extension for that one case.

PDF parsing uses `unstructured[pdf]` (poppler + tesseract) rather than `PyMuPDF` — a deliberate choice after flagging that PyMuPDF is AGPL-licensed, which isn't a "we'll deal with it later" concern for anything meant to leave a personal sandbox. DOCX/PPTX/Markdown keep their native-library parsers (`python-docx`, `python-pptx`, `markdown-it-py`) rather than being funneled through `unstructured` too — `unstructured` earns its dependency weight specifically for PDF's harder extraction problem (layout analysis, OCR fallback), not for formats with a straightforward native parser already available.

Every format-specific parser converges on one common `Element` schema (type, text, metadata: source file, position, page/slide number) — everything downstream (chunking, citations) works against that one shape, never against a format-specific structure.

## 5. Chunking

Five strategies live behind one `Chunker` interface: fixed-size, recursive character, semantic (embedding-similarity boundary detection), structure-aware (splits on document structure — headings, sections), and parent-child (structure-aware "parent" sections, each further split into smaller "child" pieces via `RecursiveCharacterTextSplitter`).

### Content-addressed chunk IDs

```
chunk_id = f"{doc_id}::{strategy}::{index}::{sha256(chunk_text)[:10]}"
```

Not purely positional (`doc_id::strategy::index`) — a hash of the chunk's *own text* is baked in. This single design choice is what makes several other things possible:

- **Idempotent re-ingestion**: unchanged text at the same position re-hashes to the same ID, so re-upserting is a no-op at the storage level, not a duplicate.
- **Chunk-level diffing on edits** (see [§12](#12-document-identity--incremental-re-ingestion)): a changed chunk gets a *new* ID; an unchanged one doesn't — the ID itself carries the information needed to tell "this changed" from "this is stale but identical," without diffing raw text at ingest time.

**Why `doc_id` has to be part of the hash, not just the text**: if `chunk_id` were `hash(text)` alone, two *different* documents that happen to share identical text (a boilerplate disclaimer, a repeated section header, common code) would collide into the *same* stored point. Whichever document was ingested most recently would silently win the citation metadata for that chunk, and deleting one document's stale chunks (an edit's cleanup step) could delete a completely unrelated document's copy of that same text. Scoping the ID to `doc_id` avoids this at the cost of never deduplicating storage across documents that happen to share content — a trade-off judged appropriate at this project's scale (see [§16](#16-known-limitations-named-on-purpose) for the fuller architecture that *would* dedupe across documents, and why it wasn't built).

### Parent-child retrieval

Children (small, ~200-character pieces) are what's actually searched — precise matching. Parents (the full section) are marked `is_parent=True` and excluded from search **natively at the store level** (a Qdrant payload filter, an Elasticsearch `bool.must_not`) — not a post-hoc application-level filter, so there's no way for a parent to leak into results by a caller forgetting to filter. On a matched child, `resolve_parent_context()` swaps the child's *text* for its parent's full text (more context for the LLM) while every other field — `chunk_id`, `source`, `pages` — keeps pointing at the child, so citations stay precise even though the model saw the fuller paragraph. If two different children of the *same* parent both rank in the top-k, only the higher-ranked one survives resolution — otherwise the LLM would see that parent's text twice for zero new information.

## 6. Embeddings

Multi-vector pattern: the raw content (text, image bytes) is kept for display; a *text projection* is what actually gets embedded and searched (a vision caption stands in for an image, a markdown rendering stands in for a table). Same embedding pipeline for every modality — nothing downstream needs to know a chunk originated from an image.

`ModelMismatchError`: `Qdrant.search()` compares the query vector's `model_id` against what's actually stored before searching. Dimension matching alone (which Qdrant already enforces) isn't sufficient — two different models can share a dimension count while encoding meaning in incompatible vector spaces, which would return confident-looking, *meaningless* results with no error at all otherwise.

## 7. Vector store — Qdrant

### How HNSW indexing actually works

Qdrant's approximate-nearest-neighbor index is a **Hierarchical Navigable Small World** graph — points connected into a multi-layer graph, top layers sparse with long-range links (like an express lane), the bottom layer dense with short-range links to every point. A search starts at the top layer, greedily walks toward the query vector until no closer neighbor exists at that layer, drops down one layer, and repeats — arriving at layer 0 already close to the true answer, then does a final local search there. This avoids a full linear scan (`O(n)`) in favor of something closer to `O(log n)`, at the cost of being *approximate* — it can miss the true nearest neighbor, traded for large speedups at scale.

Three parameters control the recall/speed/memory trade-off directly:

| Parameter | What it controls | Effect |
|---|---|---|
| `m` | max connections per node | higher → better recall, more memory |
| `ef_construct` | candidates considered while *building* the graph | higher → better graph quality, slower build |
| `ef_search` | candidates considered at *query* time | higher → better recall, slower query, exposed **per-call** (no rebuild needed to tune it) |

### Blue-green collection versioning

`collection_name` is a Qdrant **alias**, not a physical collection — `search()` always reads through it. `create_collection()` builds a new, uniquely-named physical collection *without* touching the alias; `publish()` atomically repoints the alias at the new collection and removes the old one. A production pipeline that instead deleted-and-rebuilt the live collection in place would have no rollback if the new version turned out broken, and no way to diff what changed to debug it — this makes that structurally impossible, since the previous version stays fully intact and queryable right up until the atomic cutover. `ensure_ready()` is the idempotent version used at service startup: create + publish an empty collection only if none exists yet, never touching an already-live one — safe to call on every boot.

Point IDs are a UUID5 hash of the human-readable `chunk_id` (Qdrant requires an int or UUID, not an arbitrary string) — deterministic, so re-upserting the same `chunk_id` updates the same point rather than creating a duplicate. The original readable `chunk_id` is kept in the payload for citation/debugging.

## 8. Keyword store — Elasticsearch

### How the inverted index + BM25 actually work

A forward index maps document → terms; an **inverted index** maps *term* → the list of documents containing it (a "postings list"), which is what makes a keyword search fast — looking up "GPU" jumps straight to the documents containing it instead of scanning the whole corpus.

**BM25** ranks the matching documents by combining three signals:
- **Term frequency**, saturating (not linear) — the 10th occurrence of a term in a document adds much less score than the 2nd, controlled by a `k1` parameter.
- **Inverse document frequency** — a term that appears in *most* documents (like "the") is a weak signal; a term appearing in only a few documents is a strong, discriminating one.
- **Length normalization** — a term appearing once in a 20-word chunk is more significant than once in a 2,000-word one, controlled by a `b` parameter.

**Why keyword search still matters next to embeddings**: exact identifiers, part numbers, and error codes are exactly what embedding similarity blurs (an embedding model represents *meaning*, and "ERR-4471" doesn't have meaning to blur toward) — BM25 matches the literal token.

**Analyzer choice**: the `standard` analyzer (lowercasing + whitespace/punctuation tokenization, *no stemming*) was chosen explicitly over Elasticsearch's fancier options — stemming risks mangling exact codes/identifiers ("CVE-2024-12345") in exchange for generalizing prose forms ("test"/"tests"/"testing") this corpus doesn't especially need. Known, documented, *not-yet-fixed* gap: the standard tokenizer splits on hyphens, so `"internal-llama-70b"` indexes as three separate tokens — still matches on any of them, but blurs exact-phrase precision. The real fix (a second, un-analyzed `keyword`-typed field for exact matching) was named and deliberately deferred, not missed.

`chunk.id` is used directly as the Elasticsearch `_id` — no UUID conversion needed here, unlike Qdrant, since ES document IDs accept arbitrary strings natively.

## 9. Hybrid indexing & consistency

`HybridIndexer` coordinates writes to both stores so "upsert into Qdrant, then index into Elasticsearch" isn't two separate, uncoordinated calls scattered through the codebase. **Not** true cross-database atomicity — Qdrant and Elasticsearch share no transaction mechanism, and building one (a single source-of-truth store both stores sync from independently, the way real search infrastructure eventually solves this) was judged disproportionate for this project's scale. What it *does* give: a persistent failure on the second write raises `IndexConsistencyError` carrying exactly which `chunk_id`s are now inconsistent, rather than a silent gap discovered later via a confusing search result — plus `check_consistency()`, which compares `list_chunk_ids()` between both stores independently to catch drift from *any* cause (a failed write, a deletion that only touched one store, manual intervention).

`delete()` mirrors `index()`'s ordering and error-handling exactly, for the same reason: vector store first, keyword store second, so a persistent failure on the second step is reported precisely instead of silently leaving one store cleaned and the other not.

## 10. Retrieval

One `Retriever.retrieve(query, method, top_k, ...)` call, method selected per-query:

- **Cosine** — a thin wrapper over the vector store's own similarity search.
- **BM25** — a thin wrapper over the keyword store.
- **MMR (Maximal Marginal Relevance)** — trades relevance against redundancy:

  ```
  MMR = argmax_{d ∈ R∖S} [ λ·Sim(d, query) − (1−λ)·max_{s∈S} Sim(d, s) ]
  ```

  Greedy iterative selection: repeatedly pick the candidate maximizing relevance minus similarity-to-already-selected. `λ=1` degenerates to pure relevance ranking (identical to plain cosine); low `λ` actively prefers a diverse set over a cluster of near-duplicates, even at some cost to raw relevance. Requires candidate vectors (`with_vectors=True`) to compute the redundancy term.

- **Hybrid (Reciprocal Rank Fusion)** — fuses cosine and BM25 rankings:

  ```
  RRF_score(d) = Σ_r 1 / (k + rank_r(d))
  ```

  summed over each ranking method `r` that returned `d`, `k=60` a standard damping constant. Fused by **rank position**, not raw score — a BM25 score (unbounded, corpus-dependent) and a cosine score (bounded, model-dependent) aren't measuring comparable things and can't be meaningfully rescaled onto each other, but "ranked #1" means the same thing regardless of which method produced that ranking. This is the real, practical answer to "how do you combine two different scoring systems."

- **Reranking** — an *orthogonal* `rerank: bool` flag applicable to any method above, not a fifth method: retrieve a broader candidate pool, then re-score it with a cross-encoder (`CrossEncoderReranker`, local `sentence-transformers`) before cutting to `top_k`. Cross-encoders score a (query, document) pair *jointly* — much more accurate than comparing two independently-computed embeddings, but too expensive to run over an entire corpus, hence "retrieve broad, rerank down" rather than "rerank everything." Only the local cross-encoder path was built; a hosted reranker (Cohere/Voyage-style) was explicitly *not*, for lack of credentials to test against — a scoped decision, not an oversight.

Since `is_parent=True` chunks are excluded from search **natively at the store level** (§5), reranking *always* operates on precise child text, never parent text — this became true unconditionally once that store-level filter was in place, not just "usually true because children tend to rank higher."

## 11. Generation

### The chain(s)

Two generation paths share the same building blocks (`assemble_context`, `parse_answer`, the grounding rules baked into each one's system prompt). `RagChain` is a pure single-shot retrieve → generate → parse pipeline, built with LangChain's LCEL (`RunnableLambda` steps composed via `|`) used purely as an **orchestration layer** — the actual model call still goes through `get_llm()` from the providers factory, so "same chain runs against a local OpenAI key and an internal company LLM, no code change" stays exactly as true in generation as everywhere else. `AgentChain` (below) is the interactive path: a hand-rolled loop, not LCEL, since "call the model, maybe call a tool, maybe loop" isn't a fixed pipeline the way single-shot retrieve-then-generate is. LangChain's own model-wrapper classes (`ChatOpenAI` etc.) were deliberately not used in either, for the same vendor-coupling reason as [§3](#3-providers-layer). State threads through `RagChain` as a dict, each step adding a key — the standard LCEL pattern for carrying auxiliary data (the retrieved context, needed again after the LLM call to map citation markers back to real metadata) alongside the main value.

### Agentic tool-calling

The original design rewrote a follow-up question into a standalone one with a separate LLM call, then always ran exactly one retrieve + one generate. Replaced with a real agent: the LLM gets one tool, `search_knowledge_base(query)`, and decides for itself — across up to `max_tool_rounds` rounds — how many searches a message needs. This is what turns "how does X compare to Y, and what's Z" into two targeted retrievals instead of one vague one, and is what let the old rewrite step (and its "Conversation so far:" text-flattening trick) be deleted outright: the model now sees real `user`/`assistant` messages for prior turns and decides for itself whether/how to search again for a follow-up.

**Rounds vs. calls**: `max_tool_rounds` caps *rounds* (one LLM turn), not raw search count — a single round can include more than one *parallel* tool call (observed live: a compound question triggered two `search_knowledge_base` calls in the same round, not two rounds). The system prompt names this distinction explicitly rather than saying "N searches," because an earlier draft's "N searches, comfortably enough for a two-question decomposition" phrasing was two bugs at once — it undercounted real capacity (parallel calls aren't one-per-round) and hardcoded an editorial claim that would go stale the moment the round default changed.

**Search-before-refusal is a state-machine invariant, not only a prompt rule**: exposing a tool to an LLM makes it available; it does not guarantee the model will call it. Observed live, the model sometimes obeyed the grounding rule too early and returned the exact refusal sentence before performing any search. It could also stop after one poorly phrased search returned no chunks, treating retrieval failure as proof that the corpus lacked the answer. The prompt now states an explicit protocol: search before refusing, and reformulate once after an empty result. Application code enforces the same boundary: a refusal before any search is replaced by a search using the original question; a refusal while the accumulated context is still empty triggers one additional model turn with `tool_choice="required"` and an instruction to use materially different terms. A refusal after nonempty evidence is accepted, because the retrieved passages may genuinely omit the requested fact. The forced reformulation is allowed only once and still consumes the existing `max_tool_rounds` budget, preventing an unproductive model from looping forever. This deliberately combines probabilistic guidance (the prompt helps the model choose a better query) with deterministic control flow (Python decides when refusal is legal).

**Append-only citation ledger**: `⟦N⟧` markers are resolved *positionally* (`parse_answer()` maps marker N to `context[N-1]`), so a marker's meaning must never change once shown to the model. Chunks accumulate across rounds in a strictly append-only list — a chunk already seen (two sub-questions surfacing the same passage) keeps its original marker rather than being renumbered. Re-sorting the ledger by relevance before the final answer, an intuitive-sounding alternative, would silently break this: the model commits to a marker number in its own generated text the moment a tool result shows it one, and renumbering afterward would resolve that marker to a *different* chunk than the one actually cited.

**Clarifying questions (human-in-the-loop)**: when a request has no resolvable referent (an unresolved pronoun, a follow-up with nothing to anchor to), the model is instructed to ask instead of guessing or searching speculatively — reusing the same exact-sentinel idiom the refusal text already used (`"CLARIFYING QUESTION: "`, checked as a literal prefix, never inferred from free-form text). This needed no new session-state plumbing: the user's reply is just their next chat message, threaded through `history` like any other follow-up. Getting a reliable trigger phrase took live iteration — "how does it compare to the baseline?" didn't trigger it at all (the model tried four search rephrasings for "baseline" before giving up and refusing, since a plausible-sounding technical term reads as worth searching for, not as unresolvable), while "can you compare it with the one we discussed earlier?" reliably did, since referencing nonexistent prior discussion is a much stronger, less searchable signal of missing context.

**Two real gaps found only by testing against a live model, never surfaced by the mocked test suite**: (1) `gpt-4o-mini` sometimes substituted an adjacent-but-different fact (P95 when asked for P99) instead of refusing, despite the prompt saying not to — fixed by naming the failure mode explicitly in the refusal rule ("even if a related but DIFFERENT fact is present, do not substitute"). (2) it sometimes cited using its own trained-in browsing-citation format (`【N†source】`) instead of the requested `⟦N⟧`, despite the prompt explicitly forbidding it — and kept doing so in roughly 1 of 3 live attempts even after that instruction was strengthened. Prompting narrowed but did not close this gap, so `parse_answer()` now normalizes the one variant actually observed back to `⟦N⟧` before parsing, rather than relying on compliance alone — the same "prompted, not enforced" lesson recurring at two different layers of the same system.

**System prompt structure**: organized into explicit `##`-headed sections (Role, The Corpus, Searching, When To Ask Instead Of Searching, Grounding And Refusal, Citation Format, Handling Document Content Safely, Conversation Context, Examples) rather than one flat rules list, plus a few-shot Examples section built on a deliberately *unrelated* fictional domain (an employee handbook). A few-shot example sharing content with the actual test/demo corpus would risk the model pattern-matching toward that specific content rather than generalizing the underlying rule — making tests look artificially better than the rule actually is.

### Context assembly

Token-budgeted, **greedy fill by rank**: include results in ranked order until the next one would exceed the budget, then stop — dropping the *tail* of the ranking (lower-relevance results), never truncating an individual chunk's text (a half-sentence of context is worse than one fewer whole chunk). Always includes the top result even if it alone exceeds budget — an empty context defeats the point of the guardrail below.

### Citations and the guardrail

The system prompt instructs the model to answer *only* from the numbered context blocks, to refuse with an exact, matchable sentence if the answer isn't present, and to cite claims inline using a distinctive marker: `⟦1⟧`, not `[1]`. That choice mattered in practice, not just in theory — plain `[N]` collides with bracketed numbers that occur naturally in source documents (footnotes, step lists, array indices) *and* in a model's own enumerated-list writing style, and either would be misread as a citation by a naive `\[(\d+)\]` regex. `⟦…⟧` is distinctive enough that it only appears when the prompt put it there.

Citations are never trusted from the model's own recall of filenames or page numbers — `parse_answer()` only extracts *which numbered marker* was used, then looks up the real `chunk_id`/`source`/`pages` from the context **we** already built. The model's job is picking which block is relevant; the mapping back to real metadata is entirely programmatic.

**Prompt injection**: context blocks are framed explicitly as *data to read*, not instructions to obey — a mitigation, not an elimination (an LLM reliably distinguishing "instructions" from "data that looks like instructions" isn't a solved problem). The limiter on blast radius is architectural, not behavioral, and it changed with the agent: `AgentChain` *does* let the model trigger a real tool call now (unlike the plain `generate()` path `RagChain` uses), but the only tool that exists is a read-only search over the corpus itself — so a successful injection can at most steer *what gets searched next*, never perform a side-effecting action. That property has to be judged fresh against any future tool added to the agent, not assumed to carry forward automatically.

## 12. Document identity & incremental re-ingestion

This is the area with the most iteration, because it surfaced a real tension worth stating precisely: a *single* identity value cannot simultaneously be (a) stable across a file being renamed, and (b) stable across a file's content being edited — because "derived from content" (needed for (a) without relying on the filename) definitionally changes the moment content changes (breaking (b)), and "not derived from content" (needed for (b)) has nothing to anchor renaming-invariance to.

The resolution actually shipped:

- **`doc_id = sha256(filename)`** — deliberately *not* a content hash. This is what makes chunk-level diffing possible: `chunk_id` embeds `doc_id` (§5), so a stable `doc_id` across an edit means only the chunks whose *text* actually changed get new IDs — the rest are recognized as already correctly stored and skipped, not blindly re-embedded. Editing one word in a 34-chunk sample document, verified directly: 29 chunks untouched, 5 re-embedded, 5 stale ones actually deleted — not 34 orphaned and 34 redone (an earlier, content-hash-based `doc_id` design had exactly that failure mode, caught and fixed).
- **`content_hash = sha256(bytes)`**, tracked separately in the `documents` table, purely to detect "nothing changed" (an exact re-upload under the *same* filename) without redoing any work to find out.
- **A global content-hash check**, independent of `doc_id`: before parsing anything, check whether this exact content already exists *anywhere* in the corpus, under *any* filename. This is what actually solved a real bug — the same file uploaded once via a single-file picker (reports a bare filename) and once via a native folder picker (reports a path-prefixed name, via the browser's `webkitRelativePath`) wasn't recognized as the same document, because the two upload paths produced two different filename strings and therefore two different `doc_id`s. Rather than normalizing filenames (guessing which of several possible naming quirks — a path prefix, Unicode normalization — was responsible in a given case), checking content globally sidesteps the question entirely.

**Named trade-off, not a bug**: renaming a file with *unchanged* content is no longer deduplicated as "the same document" the way it briefly was in an earlier iteration — a rename is a new `doc_id`. Two genuinely different files that happen to share a leaf filename (`notes.md` in two unrelated folders) will collide into one `doc_id` if both are ever ingested. Deletion of orphaned chunks on an edit (`Chunk_ids present before, absent in the new chunking`) is computed by filtering `list_chunk_ids()` for the `doc_id::` prefix every chunk_id already carries — no separate tracking table needed, since the scoping is already baked into the ID itself.

The fully general fix — content-addressed chunk *storage* decoupled from document *membership*, the way git separates content-addressed blobs from the tree/commit structure that tracks which blob belongs to which path — would get every property at once (including deduplicating identical content *across* unrelated documents), at the cost of a real architecture change: a many-to-many storage model instead of one-point-per-chunk, reference-counted deletion, and citation logic that can attribute a chunk to more than one document. Named explicitly as the "textbook correct" answer and explicitly not built, as disproportionate to this project's single-user scale.

## 13. API layer

FastAPI, `async def` route handlers wrapping every blocking call (Qdrant/ES clients, `litellm`, local model inference) in `starlette.concurrency.run_in_threadpool` — without that, a single slow embedding call would block the entire event loop and serialize every other request behind it, silently defeating the point of declaring the endpoint `async` at all.

**Idempotent-ready ingestion** short-circuits on a known, unchanged `doc_id`+`content_hash` *before* touching the file — parsing, chunking, and embedding are skipped entirely, not merely deduplicated after the fact. `IngestResponse.status` distinguishes `"ingested"` / `"already_ingested"` / `"duplicate_content"` so a caller (and the frontend) can tell those apart instead of everything looking like a fresh ingest.

**`ensure_ready()` vs. blind recreation at boot**: Elasticsearch's `create_index()` is destructive (drops and recreates), so calling it unconditionally on every service startup would silently wipe a previously-indexed corpus on every restart. `ensure_ready()` checks existence first — create only if missing, otherwise a no-op — and is what's actually safe to call on every boot.

**Self-healing sqlite schema**: `CREATE TABLE IF NOT EXISTS` runs on *every* connection now, not once at `Database.__init__`. Found the hard way — `tests/live/wipe_db.py` is explicitly designed to be safe to run against an already-running server, but schema-once-at-construction meant deleting the underlying file out from under a live process left every later query hitting "no such table" until that process restarted. Cheap, idempotent, and closes exactly that gap.

**`DELETE /documents`** wipes every chunk in both stores (unioning both stores' `list_chunk_ids()` rather than trusting either alone, so it also repairs any pre-existing drift) and every row in `documents` — deliberately leaves query/feedback history alone, since that's a log of past activity, not corpus state, and stays meaningful after the corpus itself is reset.

**`DELETE /documents/{doc_id}`** is the single-document version of the same idea, scoped rather than wholesale: `HybridIndexer.delete_document(doc_id)` filters both stores' `list_chunk_ids()` by `startswith(doc_id)` before unioning and deleting — safe because `chunk_id` is `f"{doc_id}::{strategy}::{index}::{hash}"` (§5) and `doc_id` itself is a fixed-length sha256 hex digest, so one document's id can never be a prefix of another's. 404s if the `doc_id` isn't in `documents` at all, rather than silently reporting zero chunks deleted for a typo'd id.

**Conversations moved server-side**: `/query` originally took a client-supplied `history` list (capped at `max_length=10`), re-sent in full on every call. Replaced with a `conversation_id`: omitted, the server creates one; passed, the server loads that conversation's history from sqlite (windowed to the last 10 turns — the same bound, just enforced server-side now instead of at the request-schema layer) and feeds it to the agent. New `conversations` and `citations` tables (the latter one row per citation — marker, chunk_id, source, `pages`/`slides` as JSON-encoded lists, and (added later) `text`/`elements` — a full snapshot of that chunk's own content at citation time, `elements` also JSON-encoded, since sqlite has no native array/object column); `queries` gained `conversation_id` and `needs_clarification` columns. Both are declared in the `CREATE TABLE` DDL for a fresh database *and* self-healed onto an already-existing `queries` table via a small `PRAGMA table_info` + conditional `ALTER TABLE` helper — consistent with this file's existing self-healing-schema property (above), rather than requiring a manual reset for what would otherwise be a breaking schema change.

`GET /conversations/{conversation_id}` reconstructs a full turn history (question, answer, citations, refused, needs_clarification) for reload/resume — deliberately *not* paired with a `POST /conversations` (creation stays implicit in `/query`, matching how most chat APIs create a thread on the first message) or a list-all endpoint (no UI surface needed one yet).

## 14. Frontend

Streamlit, talking to the API **only over HTTP** — never importing `multimodal_rag` directly, which keeps the API a real architectural boundary rather than just an internal layering convention on paper.

Folder ingestion uses `st.file_uploader(accept_multiple_files="directory")` — a genuine native-OS folder picker (not a hand-rolled in-app directory browser, which was tried first and turned out unreliable for selecting subfolders in real browser use). Junk filtering (Office `~$` lock files, dotfiles, OS metadata) happens client-side before anything reaches `/ingest`, since the native folder picker has no per-file filtering of its own once a folder is chosen — and it has to live *outside* the surrounding form, since a form only exposes selected files to the script after submission, which would make it impossible to preview what's about to be skipped before committing to the click.

**Metrics staleness, and why it happened**: the Metrics/Documents panels sit earlier in the script's top-to-bottom render order than the chat input and feedback buttons. Streamlit reruns the whole script on every interaction — but *within one run*, code executes in the order it's written, so the metrics fetch (reading current state) happened *before* that same run's query or feedback mutation. Fixed with `st.rerun()` right after those specific mutations; `st.toast()` (not `st.success()`) for the resulting confirmation, since toasts are specifically designed to survive an immediate rerun where a normal message would be cut off mid-render.

**From a form to a chat**: the single question/answer form was replaced with `st.chat_message`/`st.chat_input`, rendering the full conversation as a scrolling transcript (`st.session_state.turns`, one entry per turn, shaped almost identically to the API's own `QueryResponse`/`ConversationMessageOut` so rendering code doesn't care whether a turn came from a live response or a reloaded `GET /conversations` call). `st.chat_input` has no per-message settings the way the old form did, so retrieval method/top_k moved into a persistent sidebar "Retrieval settings" expander instead — a necessary consequence of the primitive, not a preference. Every assistant turn gets its own 👍/👎 (keyed by that turn's `query_id`), not just the most recent one; the always-visible optional-comment text box was dropped in the same move, in favor of a compact per-message control closer to how real chat apps handle this.

**Resumable via URL, with an explicit fallback boundary**: `conversation_id` lives in `st.query_params`, not just session state, so a refreshed tab reloads the transcript from the server instead of losing it. An unknown/stale id in the URL (a bookmark after a DB wipe) degrades to a fresh conversation rather than erroring — the same `try/except httpx.HTTPError` discipline the `/health` check already used, reused rather than reinvented. One asymmetry accepted deliberately: `retrieved_chunks` (the full retrieved-but-uncited candidate set) isn't part of what the server persists, so a reloaded turn has no "Retrieved chunks" expander, while a turn generated live later in the same session does. Citations are the exception, not victim to this gap: each one carries its own `text`/`elements` snapshot taken at citation time (see §13), so a reloaded turn's citation buttons open the same real chunk-detail modal a live turn's do — this was the original design's actual complaint ("why can't I view details of chunks of previous conversations") and is why citations, specifically, don't need `retrieved_chunks` to work.

## 15. Testing philosophy

**Real services over mocks, at the store layer.** `QdrantStore`/`ElasticsearchStore` tests run against actual local Qdrant/Elasticsearch instances (via `docker-compose.yml`), not mocked clients — a store class is mostly a thin wrapper around real network calls, and mocking the client would mostly test the mock's fidelity to the real API, not the store's actual behavior. Provider-layer and chain-layer tests use fake/duck-typed implementations instead (`FakeEmbedder`, `FakeLLM`) — deterministic, free, fast, and appropriate once the layer under test doesn't depend on a *specific* backend's real behavior, just on the interface contract.

**`retry_with_backoff` tests mock `time.sleep`**, not the retried operation — the point under test is the retry *logic* (does it retry the right number of times, does it eventually raise), and real sleeps would make the suite slow for no benefit.

**Live scripts, separate from the automated suite** (`tests/live/`): `start_all.py`, `wipe_db.py`, `stop_stores.py` — manual convenience tooling for actually clicking around the running app, explicitly *not* named `test_*.py` so pytest never collects them as tests. `start_all.py`'s shutdown handling specifically survives a second, impatient Ctrl+C during cleanup (escalates to a hard kill instead of crashing with a raw traceback) — caught via an actual live double-interrupt test while building it, not assumed correct.

**A session-wide `tests/conftest.py` autouse fixture blanks `LANGFUSE_*` env vars for every test.** Once retrieval tracing (§17) lives inside `Retriever.retrieve()` itself, *any* test that constructs a real `Retriever` -- not just tests that explicitly opt into exercising tracing -- reads real `Settings`, including whatever real Langfuse credentials happen to be sitting in a developer's own `.env.local`. Caught live, not by inspection: an ordinary `pytest tests/` run sent ~15 real `"retrieve"` traces to a real Langfuse Cloud project once `.env.local` had working credentials in it. Same class of bug as "silent real LLM call in tests," caught and fixed earlier for LLM/embedder providers -- a test must never depend on, or leak data to, a real external service just because local developer config happens to make one reachable. The fixture sets the string fields to `""` (not deletes them) specifically because pydantic-settings' precedence is OS env var over `.env` file -- deleting the OS var would just let the file's real value show back through; `LANGFUSE_ALLOW_CLOUD_HOST` (a `bool` field, no blank-means-unset normalization) needs an explicit `"false"` for the same reason. Tests that specifically exercise `get_langfuse_client()`'s own configuration logic (`tests/test_tracing.py`) monkeypatch `get_settings` directly, per test, and are unaffected by this fixture either way.

## 16. Known limitations, named on purpose

Each of these was a real judgment call, not an oversight — named here so they read as decisions, not gaps discovered later:

- **No cross-database transactions** between Qdrant and Elasticsearch (§9) — a single source-of-truth store both stores sync from independently would remove this, at real architectural cost.
- **No content deduplication across different documents** that happen to share text (§5, §12) — the fully general fix is a git-blob-style content-addressed storage layer decoupled from document membership; not built, named explicitly as the "textbook correct, more capable" answer.
- **No collection-name-scoped sqlite state** — `documents`/`queries`/`feedback` are one global table each, not partitioned per Qdrant collection. Only matters once more than one corpus is meant to coexist behind one API process, which hasn't come up yet.
- **Elasticsearch's standard analyzer splits on hyphens** (§8) — blurs exact-phrase precision for hyphenated identifiers; the real fix (a second `keyword`-typed field) is named, not built.
- **No schema migration framework** for the sqlite state, with one narrow exception — `queries`' `conversation_id`/`needs_clarification` columns are self-healed onto an existing table via `PRAGMA table_info` + `ALTER TABLE` (§13), because that specific change was cheap enough to do properly. A less trivial schema change would still require a full `wipe_db.py` reset, not an in-place migration. Proportionate for a single-user learning project; would not be for anything with real data at stake.
- **Local, containerized dev has no MPS acceleration** — Docker on macOS runs inside a Linux VM with no GPU passthrough to Apple Silicon, so a containerized local stack falls back to CPU even though running the app natively on the same Mac gets MPS.
- **Grounding remains partly behavioral even where refusal sequencing is enforced** (§11) — search-before-refusal is now a code-level state-machine invariant, but a model can still misjudge nonempty evidence, substitute an adjacent fact instead of refusing, or cite using its own trained-in format. The citation-format case has a narrow code-level normalization for the variant observed live; factual entailment still needs evaluation rather than being fully enforceable by orchestration code.
- **`retrieved_chunks` isn't persisted, only citations are** (§13) — a reloaded conversation can show what was cited (citations carry their own `text`/`elements` snapshot, taken at citation time, so their detail modal works after a reload) but not the full retrieved-but-uncited candidate set from the original turn, which stays live-turn-only. A deliberate scope decision, not an oversight; revisit if that broader history ever matters for evaluation.
- **No access control on conversations** (§13) — `conversation_id` is a bearer-style identifier with no ownership check, same trust model this app already has for `query_id`/`doc_id`. Fine for a single-user learning deployment, not for anything multi-tenant. (Listing and deleting conversations are both built — see §13/§14 — it's specifically *authorization* that's absent.)

## 17. Evaluation and observability

**Two independent metric layers, deliberately kept separate.** Retrieval metrics (`evaluation/retrieval_metrics.py`: `recall_at_k`, `mrr`, `ndcg_at_k`) are pure arithmetic over a ranked `SearchResult` list against a golden item's `expected_sources` — no LLM calls, no cost, deterministic. Generation metrics (`evaluation/judge.py`: faithfulness, relevance) are hand-rolled LLM-as-judge scores, not RAGAS — RAGAS pulls in its own `langchain`/`datasets` dependency tree that needs reconciling with the existing `litellm==1.85.0` pin, and doesn't know about this project's `LLMProvider` ports/adapters abstraction. `score_faithfulness(answer, context)` deliberately does NOT take the question (a question-aware judge risks rewarding "sounds like a good answer" instead of "is actually supported" — see the P95-for-P99 reasoning below); `score_relevance(question, answer)` deliberately does NOT take the context, for the same reason in reverse. An answer can be fully relevant and fully unfaithful at once (addresses the question, but isn't actually grounded in what was retrieved) — that's exactly the case independent scoring is built to catch, and a single fuzzy "is this good" score would hide.

**The golden set (`data/golden_set.json`) needs topical competition to mean anything.** Built against 5 documents that deliberately share vocabulary ("latency", "embedding", "index") without sharing content — a golden set with too few, too-distinct documents saturates recall@k at ~1.0 for every method regardless of ranking quality, since there's nothing for a bad retriever to actually get wrong. `_TOP_K` in `run_eval.py` is deliberately smaller than the corpus size for the same reason: recall@k can only fail when fewer documents fit in top-k than exist in the corpus. Caught live, not reasoned out in advance — an early 2-document version of the golden set, and later a `_TOP_K=5` run against a 5-document corpus, both saturated for exactly this reason before being fixed.

**Refusal-accuracy is scored separately from faithfulness/relevance, not through them.** A golden item with `expect_refusal: true` (e.g. "what was the P99 latency" when only P95 exists) makes no factual claims and isn't trying to answer the question, so faithfulness/relevance judges built for substantive answers would misjudge it — worse, a question-aware faithfulness judge shown "P95 exists, P99 doesn't" could reason a refusal is unnecessary given the closely-related data available, and reward exactly the P95-for-P99 substitution failure the agent's own system prompt (§11) already explicitly forbids. `refusal_accuracy` is a plain correctness check instead (did the chain refuse, yes/no) — the real test of hallucination resistance on the hardest case, without misapplying a judge built for a different job.

**`/metrics`'s `avg_latency_ms`/`feedback_rate` stay deliberately shallow** — no p95, no cost-per-query. That split is intentional: this endpoint is the cheap, always-on local summary (timed around the *whole* `agent.answer()` call, not one LLM completion, since a compound question can trigger multiple search/generate rounds and "latency of this query" means the full round-trip a caller actually waited through); percentile breakdowns and cost belong to Langfuse tracing, which computes them natively per-trace.

**Langfuse tracing is wired manually, not via litellm's `success_callback=["langfuse"]`.** This was a real, non-obvious blocker, not a style preference: `litellm==1.85.0` (pinned deliberately — see the LLM section) only declares compatibility with the OLD v2 langfuse client (`langfuse==2.59.7`), which itself pins `wrapt<2.0` — directly incompatible with `unstructured[pdf]`'s `wrapt>=2.1.1`, already a hard ingestion dependency. Confirmed by direct inspection, not assumption: litellm's `LangfuseLogger` does `langfuse.version.__version__`, a module that doesn't exist at all in the modern (v4, OpenTelemetry-based) client this project actually installs. `tracing.py` instruments `litellm.completion()` calls manually instead, via `Langfuse.start_as_current_observation(as_type="generation"|...)`. Nesting (every search + every LLM call of one `/query` turn under one trace, every turn of one conversation grouped under one session) comes for free from OpenTelemetry's own context propagation — no manual `trace_id` threading through `LLMProvider`'s interface was needed, which matters because that interface is implemented by fake test doubles in a dozen+ test files; adding a required parameter there would have broken all of them for a purely optional feature.

**Retrieval is instrumented at the source (`Retriever`), not reactively from `AgentChain`'s callback.** The original approach logged one `create_event()` (a point-in-time marker, no duration) from `AgentChain.answer()`'s existing `on_tool_call(round_index, query, results)` hook -- but that hook fires *after* a search already completed, with no start time to measure against, and it only covered what one specific caller (`AgentChain`) chose to report. Superseded by wrapping the actual embedder/Qdrant/Elasticsearch/reranker calls directly inside `Retriever.retrieve()` (`retrieval/retriever.py`) with `tracing.traced_span()` -- a generic sibling of `traced_generation` using Langfuse's own `"retriever"`/`"embedding"` observation types where they fit. This gives real per-step timing (`retrieve` as one parent span, `embed_query`/`qdrant_search`/`elasticsearch_search`/`rerank` as its timed children) and makes retrieval tracing automatic everywhere `Retriever.retrieve()` is called -- `RagChain`, `demo.py`, `run_eval.py` too, not just the interactive `/query` path via `AgentChain`. `on_tool_call` itself is untouched and still serves `demo.py`'s console printing; `routers/query.py` no longer needs to wire it into tracing at all. The span's `output` is a compact per-result summary (source, score, pages/slides, a ~300-character text preview) -- deliberately not the full `SearchResult` (whose `.elements` can carry base64 image data, and whose `.text` can be the full resolved-parent section, up to 8000 characters) -- so a trace stays legible in the UI rather than becoming a payload dump.

**The public Langfuse Cloud is refused by default, independent of `allow_external`, with a separate deliberate opt-in.** `allow_external` answers "may this profile call any external service at all" — true on an ordinary company laptop, since it needs to reach the company's own external LLM gateway. That is a different question from "may this specific data (real user questions, answers, retrieved document content) be handed to a third party's cloud," which has to default to no even when the first answer is yes; conflating the two would mean a laptop set up to reach an approved company AI endpoint could just as easily leak confidential query content to `cloud.langfuse.com` the moment someone pasted in API keys. So `get_langfuse_client()` blocks `cloud.langfuse.com` and its regional variants (`us.`/`eu.cloud.langfuse.com`) before the `allow_external` guard ever runs, and separately refuses to default a blank `LANGFUSE_HOST` to that same address the way the SDK itself would — tracing only activates once someone explicitly names a real (intended to be self-hosted) host. A second, independent setting, `langfuse_allow_cloud_host` (`LANGFUSE_ALLOW_CLOUD_HOST` in `.env`), lifts the cloud-specific block for the rare, genuinely-fine case — e.g. a personal dev machine with no confidential documents — but only that block: an air-gapped profile (`allow_external=False`) still refuses the cloud even with the opt-in set, since the general external-host guard runs independently afterward. The existing `allow_external`/internal-host guard (§ privacy guard) still applies on top, for any *other* external address on an air-gapped profile. Every blocked case disables tracing with a logged warning rather than raising — tracing must never be a reason a real query fails, but silently going dark would leave a developer unable to tell why traces never show up.

**Every direct Langfuse SDK call is wrapped defensively, not just the "not configured" case.** `get_langfuse_client()`, `traced_query`, `traced_span`, `traced_generation`, and `record_generation_result` all originally only handled tracing being *unconfigured* as a no-op — a Langfuse hiccup *after* successful configuration (host unreachable, service down, a network blip) could still have broken a real, already-succeeded query. Two failure classes needed separate fixes: (1) `get_langfuse_client()`'s own `Langfuse(...)` constructor wasn't guarded, and worse than crashing once — `@lru_cache` doesn't cache a raised exception, so every future request would retry (and re-fail) construction forever, once configured; fixed by catching the failure and returning `None`, which *is* what gets cached. (2) every span open/close and `.update()` call needed its own try/except, especially `record_generation_result()`'s, which runs right after a real, successful LLM response comes back — a tracing failure there must not be able to take that already-obtained answer down with it. `_safe_enter`/`_safe_exit` helpers centralize this for the open/close case; verified with tests that inject failures at each exact point and confirm the wrapped work still completes, plus one confirming a REAL exception from the wrapped business logic still propagates normally (tracing swallows only its own failures, never a real one).

**`traced_query`'s own "query" span silently had no `input`/`output` for a while — caught by the user noticing it in the Langfuse UI, not by review.** Every other observation (`generate_with_tools`, `embed_query`, `qdrant_search`, ...) was built with `input=...` at creation and had its `output` attached before closing; `traced_query`'s `start_as_current_observation()` call was only ever given `metadata={"query_id": ...}`, and the function yielded nothing, so `routers/query.py` had no handle back to the span to attach the final answer to even if it had wanted to. Fixed by having `traced_query` take the question as a parameter (set as `input` at creation) and yield the span itself, so the caller calls `update_span_output(span, result.answer)` once the real answer is known — the same pattern `traced_generation`/`traced_span` already followed; `traced_query` was just the one call site that never got it.

**Since retrieval tracing moved inside `Retriever` itself, any test constructing a real `Retriever` — not just tests deliberately exercising tracing — was silently reading real `Settings`, including real Langfuse credentials sitting in a developer's own `.env.local`.** Caught live, not by inspection: an ordinary `pytest tests/` run sent ~15 real `"retrieve"` traces to a real Langfuse Cloud project once `.env.local` had working credentials in it — the exact "silent real network call in tests" failure mode already caught once for LLM/embedder providers, recurring here for a different subsystem. Fixed with a session-wide `tests/conftest.py` autouse fixture that blanks `LANGFUSE_*` env vars for every test. The fixture sets the string fields to `""`, not deletes them — pydantic-settings' precedence is OS env var over `.env` file, so deleting the OS var would just let the file's real value show back through; `LANGFUSE_ALLOW_CLOUD_HOST` (a `bool` field, no blank-means-unset normalization) needs an explicit `"false"` for the same reason. Tests that specifically exercise `get_langfuse_client()`'s own configuration logic (`test_tracing.py`) monkeypatch `get_settings` directly, per test, and are unaffected either way.

**The golden set now also runs as native Langfuse Experiments** (`evaluation/langfuse_experiment.py`, `uv run python -m multimodal_rag.evaluation.langfuse_experiment`) — one dataset run per retrieval method, so "hybrid+rerank beat cosine on faithfulness" is a comparison Langfuse's own UI renders natively (per-run averages, run-vs-run diffing over time via a real clickable Dataset Run URL), not just a table `run_eval.py` prints once and forgets. This is additive, not a replacement — `run_eval.py`'s console-only comparison still exists and needs no Langfuse configuration at all, which matters on a profile (e.g. the air-gapped server) where Langfuse may never be set up.

`data/golden_set.json` is synced into a Langfuse Dataset on every run via `create_dataset`/`create_dataset_item` — both verified live to be genuine upserts keyed by name/id (calling either twice with the same name/id updates the existing one in place, no duplicates), so this is safe to call unconditionally rather than needing an existence check first, and a golden-set edit (a new question, a corrected `expected_sources` list) shows up on the next run automatically. Each golden item's own `id` is reused as the dataset item id specifically so this stays true.

The actual scoring logic isn't reimplemented for Langfuse — `run_experiment()`'s `evaluators` are thin adapters around the exact same `retrieval_metrics.py`/`judge.py` functions `run_eval.py` already uses and already has unit tests for. `recall_at_k`/`mrr`/`ndcg_at_k`'s signatures were widened from `list[SearchResult]` to a structural `HasSource` Protocol (they only ever read `.source`) so a lightweight `_SourceOnly` stand-in works too — deliberate, not incidental: the experiment task returns a JSON-serializable summary (`retrieved_sources: list[str]`, a plain answer string, refusal flag, assembled context text), never real `SearchResult` objects, so a trace's `output` never risks carrying `.elements`' possible base64 image data the way passing the real objects through would have. Faithfulness/relevance evaluators catch `JudgeParseError` themselves and return no evaluation for that item rather than letting a malformed judge response take down the whole experiment run — same "one bad item shouldn't sink the batch" precedent `run_eval.py`'s own judge-failure counting already established.

## 18. Tabular data — embedding vs. generation diverge for tables

**A table's LLM summary was computed since early in this project but never actually used.** `ingestion/tables.py`'s `summarize_table()` has been called by every format parser with a native table (PDF, DOCX, PPTX, Markdown) from early on, storing the result on `Element.table_summary` — but `chunking/text.py`'s `element_text()` (what actually becomes `Chunk.text`, i.e. what gets embedded and searched) only ever read `element.text`, the raw markdown rendering. Found by tracing `table_summary` through the whole pipeline on request, not by design review: it was set at parse time and read nowhere else. In effect, every table was searched via its raw markdown — mostly punctuation and short repeated cell tokens, which embeds poorly for semantic matching — while images/charts, via the same `element_text()` function, *did* get their vision-LLM `description` embedded, exactly the multi-vector pattern tables were supposed to get too.

**Fixed by making `element_text()` prefer `table_summary` for `ElementType.TABLE`, falling back to the raw markdown only when no summary exists** (unconfigured LLM, or a failed `summarize_table()` call — it already fails soft, returning `None`). This is a one-line change with an outsized effect: it fixes retrieval for every table across every existing parser, not just new ones.

**Embedding and generation had to be made to diverge, since they'd shared one field.** Once a table's embedded text is a short summary, the generator can't be shown that same summary — it needs the real numbers to answer a question about them, not a paraphrase. The fix reuses infrastructure that already existed for a different reason: `Chunk`/`SearchResult` already carry an `elements: list[ChunkElement]` snapshot of the original elements behind a chunk (built for letting the frontend display "an actual rendered table, an actual image" instead of only the flattened blob), and `ChunkElement.text` already holds the *raw* table markdown, never the summary — no new field was needed. `generation/context.py` gained `_generation_text(result)`, which reconstructs the real per-element text from `result.elements` (raw table markdown for tables, vision description for images/charts — unchanged from what's embedded, since only tables diverge) whenever any table element is present, and falls back to `result.text` for everything else — meaning it's a no-op for non-table chunks and only actually changes behavior where a table is involved. Both `format_context_block()` (what the generator reads) and `assemble_context()`'s token budgeting were switched to it — budgeting against the cheap embedded summary while the real (potentially much larger) table is what actually gets sent would have silently let the true token budget blow past what was ever counted.

**Known, accepted narrow limitation, not engineered around:** `elements` is the whole parent SECTION's elements even on a raw, un-resolved child chunk (`ParentChildChunker` assigns the same `parent.metadata.elements` to every child in that parent's group), so `_generation_text` can't distinguish "just this child's slice" from "the whole section" if a caller ever generated directly from a child with `resolve_parent_context=False` and that section contains a table. No real call site does this today — every one (`routers/query.py`, `run_eval.py`, `run_expert_eval.py`, `langfuse_experiment.py`) explicitly passes `resolve_parent_context=True` — so this was named rather than built around, per "don't design for hypothetical future requirements."

## 19. CSV/Excel ingestion — row-batching instead of one-Element-per-table

**Real spreadsheets break the existing table model.** `ingestion/tables.py` turns a whole table into one `Element` — fine for a hand-authored, small DOCX/PDF table, but a CSV or Excel sheet can be hundreds or thousands of rows. One giant `Element` would either blow past a reasonable `summarize_table()` LLM call, or get mid-row-sliced downstream by the character-based `ParentChildChunker` with no idea where a row boundary is — misaligned columns, no header, useless for retrieval.

**New shared module `ingestion/tabular.py`** batches rows into groups of `ROWS_PER_ELEMENT` (30, a starting point — not golden-set-tuned the way `child_chunk_size` was), rendering the header at the top of *every* batch via the same `rows_to_markdown()`/`summarize_table()` helpers `tables.py` already provides — reused, not reimplemented. Each batch becomes its own self-contained `TABLE` Element: never split mid-row by construction (the batching *is* the chunking, done once at parse time), and independently self-describing regardless of which part of a large sheet it came from. `csv_.py` (Python's stdlib `csv` module, no new dependency) and `excel.py` both build on this.

**Deliberately does not try to detect a "real" header row among leading title/note rows.** Real spreadsheets often have a few rows of free text above the actual column header — reliably telling those apart from the real header (merged cells, multiple header rows, notes below instead of above, more than one table per sheet) isn't a problem a heuristic can be trusted to get right. Every batch is rendered as-is, whatever rows are actually in it; the LLM summary this now feeds into embedding (§18) is what's relied on to describe what a batch actually contains even when the first row of a batch isn't really a header — a summary just reads the batch, it doesn't need to know which row is which.

**Excel support (`ingestion/excel.py`, `openpyxl`) is `.xlsx` only, deliberately.** Legacy `.xls` needs a different, largely unmaintained library (`xlrd`, which itself dropped `.xlsx` support when maintenance wound down), and `openpyxl` doesn't support it at all — not worth a second dependency for a format phased out over a decade ago. Each worksheet is treated as its own logical table (one call into the same `tabular.rows_to_elements` CSV uses, with `sheet=worksheet.title` — no attempt to detect more than one table per sheet, same "don't guess at structure" choice as the header row). Loaded via `data_only=True` so a formula cell reads Excel's own last-calculated value ("42"), not the formula string ("=SUM(A1:A10)") — the value is what's citable and matchable; the formula isn't.

**Embedded pictures are extracted through the same vision pipeline DOCX/PPTX already use** (`ImageDescriber`, one instance per workbook) — often where the real insight in a real spreadsheet actually lives, in a chart someone pasted in as an image, not just the raw numbers. This is why `openpyxl.load_workbook()` is called WITHOUT `read_only=True`: read-only mode is openpyxl's own documented tradeoff that drops access to embedded pictures entirely, and reusing one workbook load for both row data and pictures matters more than read-only's memory savings at this project's scale. Reading them at all requires `worksheet._images` / `image._data()` — openpyxl's own PRIVATE API, since there's no public accessor for embedded pictures in an existing file at all (confirmed by research, not assumed: openpyxl's image/chart classes are built for *writing* new files, not parsing existing ones). Flagged explicitly as a fragility risk that could silently break on an openpyxl upgrade, not hidden behind a normal-looking public call.

**A native Excel CHART (built live from cell data, not a pasted-in picture) is a genuinely different, harder problem — researched, not guessed at.** Confirmed via openpyxl's own documentation: it cannot read an existing chart's definition at all, only create new ones — reading `worksheet._charts` on a loaded file returns nothing. The commercial alternatives that *can* render a chart to an image (e.g. Spire.XLS) have real free-tier limits (a 3-page cap on Excel-to-image conversion) and cost money unlimited; LibreOffice headless conversion is free but has no confirmed way to export a single isolated chart rather than a whole rendered sheet, and would add a full office-suite runtime dependency. The approach actually taken instead (`excel_charts.py`) needs neither: a `.xlsx` is just a ZIP of OOXML XML parts, and a chart's own definition lives at `xl/charts/chartN.xml` in the standard, documented chart schema — readable directly via stdlib `zipfile` + `xml.etree.ElementTree`, no new dependency, no license, no extra runtime. This describes what the chart's DATA says (type, title, series, referenced ranges resolved against the sheet's own cell values, via the LLM the same way `summarize_table()` already describes a table) rather than what the chart visually looks like (colors, manual annotations aren't in the data model) — the right fidelity for "what insight does this communicate," not a substitute for "what does it look like."

**Charts aren't named per-sheet in a `.xlsx`, so attributing one to the worksheet it's actually on needs the real OOXML relationship chain, not a guess.** `xl/charts/chart1.xml` doesn't say which sheet it belongs to — the file only says a chart exists somewhere in the workbook. `charts_for_worksheet()` follows the real chain: `worksheet._rels` (openpyxl's own private but already-resolved link — it saved having to hand-parse `workbook.xml`'s sheet-name-to-part-name mapping) gives the worksheet's drawing part (e.g. `xl/drawings/drawing1.xml`); that drawing's own `_rels` file (read directly, since this part isn't exposed through openpyxl at all) lists the charts it actually embeds. Verified empirically against a real openpyxl-generated chart, not assumed correct from reading the OOXML spec alone — including resolving a series' cell-range reference (`'Sheet1'!$B$2:$B$4`) into real values via `openpyxl.utils.cell.range_boundaries()` plus the workbook already loaded for row data, rather than hand-rolling A1-notation parsing.

**Scoped to "category axis" chart types (bar/column/line/area/pie), with a named fallback for the rest.** These all share the same `<cat>`/`<val>`/`<tx>` series shape in the chart schema; scatter/bubble/stock/surface/radar charts use different reference tags (`<xVal>`/`<yVal>`, ...) this parser doesn't attempt to resolve. Rather than silently dropping those charts or crashing on them, an unsupported type still produces a minimal type+title description — "a bar chart named X, data series could not be parsed" is more honest and more useful than nothing at all.
